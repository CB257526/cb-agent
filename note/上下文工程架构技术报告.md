# 上下文工程架构技术报告

当前 cb-agent 的正式 LLM 请求路径是 OpenAI-compatible Chat Completions。

## Prompt 构造

`AgentSession._build_chat_messages()` 使用固定顺序构造请求：

1. 首条 `system`：只放稳定静态规则，由 `get_static_system_prompt()` 生成。
2. 已提交历史：保持 OpenAI Chat 协议形状，包含 `user -> assistant.tool_calls -> tool -> assistant`。
3. 运行时上下文：由 `get_dynamic_context_prompt()` 生成，并作为低权限 `<context-update>` user message 追加。
4. 当前用户消息：放在请求末尾。

这样做的目标是让 provider 的隐式 prefix cache 更容易命中：system 和历史前缀尽量稳定，时间、env、memory、MCP instructions、session state 等动态内容只追加在尾部附近。

## 工具 Schema

`ToolRegistry` 的工具输出按工具名排序：

- `get_tools_description_openai_schema()`
- `list_tools()`
- `get_all_tools()`

工具 schema 是 Chat 请求体的一部分，排序稳定可以避免注册时机影响缓存前缀。

## 压缩与历史

常规请求和工具循环都不改写旧 tool result 内容。工具返回时先经过 `result_cap`：单条结果按 Codex 风格限制为 10K tokens，并以约 40K UTF-8 bytes 做硬兜底；超大结果在进入消息历史前就持久化并替换为稳定 preview。`file_read` 保留原文件路径和分页元数据，只缩短 `content`，不复制原文件。后续工具轮次只向消息尾部追加 assistant/tool 消息。

cb-agent 还保留 40K tokens/160K bytes 的同轮批量保护，以弥补当前没有 mid-turn compact 的差异。批量处理发生在结果首次追加到 `messages` 之前，只规范化本轮新结果，不回写旧 history，因此不会截断已经建立的 provider cache 前缀。

上下文过大时走 preflight、post-turn、手动 compact 或完整窗口阻断，让历史在明确 boundary 之后重新稳定追加。本地 microcompact 已移除，因为它会在请求中段替换旧工具结果，导致 provider 的连续前缀缓存从改写点开始失效。

本地 `context_update` 会进入内部 history，用于下一轮 append-only 前缀；`export_history()` 会过滤它，避免 UI 把运行时上下文显示成普通对话。

## Usage 观测

usage 解析支持：

- OpenAI: `prompt_tokens_details.cached_tokens`
- SiliconFlow/DeepSeek 兼容字段: `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`

事件层 `TokenUsage` 会透出 `cached_prompt_tokens`、`prompt_cache_hit_tokens`、`prompt_cache_miss_tokens` 和 `cache_hit_rate`，用于观察真实缓存命中。
