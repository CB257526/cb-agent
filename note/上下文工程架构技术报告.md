## 一、概述

本次重构将 cb-agent 的上下文工程模块从旧的 **GSSC 流水线**（Gather → Sort → Split → Compose，即 `context/builder.py` 861 行 + `context/markdown_memory.py` 316 行）替换为对齐 **Claude Code 设计**的新架构。核心思想是将 system prompt 的组装过程拆分为六个独立、可组合、可测试的模块，围绕四个核心抽象组织：

| 抽象 | 职责 | 对应 Claude Code 源码 |
|---|---|---|
| **Section** | 延迟计算的字符串生产单元 + LRU 缓存 | `systemPromptSections.ts` |
| **Boundary** | 静态段与动态段的切分标记 | `prompts.ts` 同名常量 |
| **Memory** | 多级 CLAUDE.md 加载与合并 | `claudemd.ts` |
| **Compaction** | 对话历史的三层压缩策略 | `autoCompact.ts` / `compact.ts` |

净增约 667 行，新增 46 个单元测试，二次 system prompt 组装从 **63ms 降至 0.38ms**（LRU 缓存命中）。

## 三、六大模块详解

### 3.1 Section 层 — `context/sections/`

#### 3.1.1 核心数据结构

`SystemPromptSection`（[registry.py:27-38](context/sections/registry.py#L27-L38)）是一个不可变的延迟计算单元：

```python
@dataclass(frozen=True)
class SystemPromptSection:
    name: str            # 缓存键,同一 prompt 内必须唯一
    compute: ComputeFn   # Callable[[], Optional[str] | Awaitable[Optional[str]]]
    cache_break: bool    # True = 每轮必重算,不读不写缓存
```

#### 3.1.2 两种 Section 工厂

| 工厂函数 | 行为 | 典型用例 |
|---|---|---|
| `system_prompt_section(name, compute)` | 可缓存,命中时跳过 compute | CLAUDE.md 加载、env_info、token_budget |
| `DANGEROUS_uncached_system_prompt_section(name, compute, reason=...)` | 每轮重算,**reason 参数强制传入** | MCP 服务的动态 `instructions` 字段 |

`DANGEROUS_uncached_*` 的命名故意大写以警示：破坏缓存意味着每次 prompt 组装都会触发 compute，且 Provider 端的 prompt cache 也会因此失效。`reason` 参数强制传入，让任何添加这种 Section 的人都必须显式说明代价。

#### 3.1.3 并发 resolve 流程

```python
async def resolve_system_prompt_sections(
    sections: Sequence[SystemPromptSection],
    cache: SystemPromptSectionCache,
) -> list[str]:
```

执行逻辑（[registry.py:87-115](context/sections/registry.py#L87-L115)）：
1. `asyncio.gather` 并发执行所有 Section 的 compute 函数
2. `cache_break=True` 的 Section → 直接调 compute，不读不写缓存
3. 普通 Section → 先查缓存（LRU 命中直接返回），未命中则调 compute 后写入缓存
4. sync compute 走 `asyncio.to_thread` 避免阻塞事件循环
5. 过滤 `None` 和空串，返回 `list[str]`

#### 3.1.4 静态段（6 个确定性函数）

[static_sections.py](context/sections/static_sections.py) 包含 6 个纯函数，放在 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 之前，可共享 `CacheScope.GLOBAL`：

| 函数 | 内容 |
|---|---|
| `get_intro_section(output_style)` | 身份声明："You are cb-agent..." |
| `get_system_section()` | 系统规则：`<system-reminder>` 标签处理、不可信内容防护、compact_boundary 处理 |
| `get_doing_tasks_section()` | 任务指导：何时直接动手、何时先澄清、何时只给建议 |
| `get_actions_section()` | 行动指南：低/中/高风险三级行动策略、禁止绕过安全检查 |
| `get_using_your_tools_section(enabled_tools)` | 工具使用规范：可用工具列表、并行调用、每步简述 |
| `get_output_efficiency_section()` | 输出效率：匹配回答长度与任务复杂度、跳过填充语 |

#### 3.1.5 动态段（6 个环境相关函数）

[dynamic_sections.py](context/sections/dynamic_sections.py) 包含 6 个闭包工厂函数，放在 boundary 之后：

| 函数 | 缓存策略 | 缓存键 | 说明 |
|---|---|---|---|
| `memory_section(memory_loader)` | 可缓存 | `"memory"` | 多级 CLAUDE.md 链 |
| `env_info_section(model, cwd, ...)` | 可缓存 | `"env_info::{model}::{cwd}::..."` | 运行环境快照 |
| `language_section(language)` | 可缓存 | `"language::{lang}"` | 用户语言偏好 |
| `session_guidance_section(enabled_tools, skills)` | 可缓存 | `"session_guidance::{tools}::{skills}"` | 工具/技能使用提示 |
| `mcp_instructions_section(mcp_clients)` | **每轮重算** | `"mcp_instructions"` | MCP 服务 instructions |
| `token_budget_section(budget_directive)` | 可缓存 | `"token_budget::{directive}"` | 用户 token 预算指令 |

`mcp_instructions` 是唯一使用 `DANGEROUS_uncached_*` 的 Section，原因是 MCP 服务可以在会话中动态 connect/disconnect，其 `instructions` 字段无稳定缓存键。

#### 3.1.6 LRU 缓存

[SystemPromptSectionCache](context/sections/cache.py#L25-L59) 的实现：

- `OrderedDict` 实现 LRU，`max_entries=100`
- `_MISSING` 哨兵区分「未缓存」与「缓存了 None」（None 是合法值：表示已确认该段不会出现，下一轮跳过 compute）
- `threading.Lock` 保护短临界区
- **模块级单例** `_GLOBAL_CACHE`：Section 名直接当 key，进程内全局共享
- `/clear` 与 `/compact` 时调用 `clear_system_prompt_sections()` 失效

**性能收益：** 测试表明，LRU 缓存使二次 system prompt 组装从 63ms 降至 0.38ms。

### 3.2 Memory 层 — `context/memory/`

#### 3.2.1 四级加载链

`MemoryLoader`（[loader.py:161-226](context/memory/loader.py#L161-L226)）按优先级从低到高加载四个层级：

```
优先级低 ──────────────────────────────────────────────→ 优先级高
(数组靠前,模型不太重视)                          (数组靠后,模型更重视)

1. Managed   %ProgramData%\cb-agent\CLAUDE.md  (Win)
             /etc/cb-agent/CLAUDE.md            (POSIX)
             → 需要管理员权限才能写入,日常基本为空

2. User      ~/.cbagent/CLAUDE.md
             ~/.cbagent/rules/*.md
             → 与 Claude Code 的 ~/.claude/ 隔离,防止共用指令

3. Project   从根目录向 cwd 逐层查找:
             CLAUDE.md / .claude/CLAUDE.md / .cbagent/CLAUDE.md
             .claude/rules/*.md / .cbagent/rules/*.md
             → 根目录最远 = 优先级最低, cwd 最近 = 优先级最高

4. Local     $cwd/CLAUDE.local.md
             → 不入版本控制,仅本机生效
```

路径查找逻辑见 [paths.py](context/memory/paths.py)。

**项目层逐层遍历**（[paths.py:60-87](context/memory/paths.py#L60-L87)）：
```python
def iter_project_memory_candidates(cwd: Path):
    # 从根向 cwd 收集所有父目录
    chain = [根, ..., cwd]
    # 对每个目录,依次查 CLAUDE.md / .claude/CLAUDE.md / .cbagent/CLAUDE.md / rules/*.md
    for directory in reversed(chain):  # 根→cwd
        for sub in ("CLAUDE.md", ".claude/CLAUDE.md", ".cbagent/CLAUDE.md"):
            if (directory / sub).is_file():
                yield directory / sub
        for rules_sub in (".claude/rules", ".cbagent/rules"):
            for md in sorted((directory / rules_sub).glob("*.md")):
                yield md
```

#### 3.2.2 @include 递归解析

[include_resolver.py](context/memory/include_resolver.py) 实现 `@include` 指令的递归解析：

**支持的路径格式：**
```
@path/to/file           → 相对当前 cwd
@./relative/path.md     → 相对 base 文件所在目录
@../parent/path.md      → 相对 base 文件所在目录
@~/home-relative.md     → 用户 home 展开
@/absolute/path.md      → 绝对路径
```

**安全措施：**
- 深度上限 `MAX_INCLUDE_DEPTH = 5`
- 循环检测: `processed: set[str]` 跟踪已解析的绝对路径
- 跳过 ` ``` ` 三反引号围栏代码块内的 `@xxx`
- 跳过行内 `` `code` `` span 内的 `@xxx`
- `@` 前不能紧跟反斜杠（转义）
- 结尾标点（`,. ! ? ; : ) ] } > ' "`）不计入路径
- `#fragment` 被剥离
- include 文件**继承父文件的 MemoryType**（防止 User CLAUDE.md include 项目文件时优先级降级）

**递归处理流程**（[loader.py:63-122](context/memory/loader.py#L63-L122)）：
```python
async def _process_memory_file(path, file_type, *, processed, depth, parent, included_via):
    # 1. 检查深度上限
    # 2. resolve 绝对路径,检查循环

    # 4. 生成 MemoryFileInfo
    # 5. 提取 @include,递归处理子文件
    # 6. 返回 [父文件, ...子文件...] (include 在数组位置靠后 = 优先级更高)
```

#### 3.2.3 Async Memoize

`_AsyncMemoize`（[loader.py:125-158](context/memory/loader.py#L125-L158)）是一个轻量级的异步记忆化装饰器：

- 缓存的是 `Future` 对象而非结果，并发 caller 共享同一次 I/O 解析
- 失败的 Future 不缓存（`pop(key, None)`），下次自动重试
- `reset_cache(reason)` 清空缓存，在 `/clear`、`/compact`、settings 热更新、cwd 切换时触发

#### 3.2.4 优先级截断

`_enforce_total_char_limit`（[loader.py:239-259](context/memory/loader.py#L239-L259)）确保 Memory 总字符数不超过 `MAX_MEMORY_CHARACTER_COUNT = 40,000`：

```
算法: 从尾部(优先级最高)向头部累加字符数
      超出 limit 时停止,保留尾部高优先级文件
      丢弃远祖目录的低优先级文件

高优先级 → Local / Project cwd 文件优先保留
低优先级 → Managed / 远祖目录文件可能被截掉
```

单文件大小限制：`MAX_FILE_BYTES = 256 * 1024`（256KB），超大文件截断读取。

#### 3.2.5 格式化输出

`format_memory_files`（[formatter.py:44-57](context/memory/formatter.py#L44-L57)）将 `MemoryFileInfo` 列表组装为注入 system prompt 的文本：

```

Contents of C:\Users\cb135\CLAUDE.md (user instructions):

<content>

Contents of C:\project\CLAUDE.md (project instructions, checked into the codebase):

```

每种 `MemoryType` 有对应的来源标签：
- Managed → "managed instructions"
- User → "user instructions"
- Project → "project instructions, checked into the codebase"
- Local → "local user instructions, NOT checked in"

#### 3.2.6 Frontmatter 解析

[frontmatter.py](context/memory/frontmatter.py) 实现最小 YAML frontmatter 解析：

- 不引入 PyYAML 等外部依赖
- 只支持 `key: value` 简单格式
- frontmatter 块由首行 `---` 与一行 `---` 包围
- 复杂结构（列表、嵌套）放正文里，frontmatter 仅承担索引/分类作用
- `strip_block_html_comments()` 用非贪婪正则剥离 `<!-- ... -->` 块级注释

### 3.3 Boundary 层 — `context/prompts/boundary.py`

#### 3.3.1 核心常量

```python
SYSTEM_PROMPT_DYNAMIC_BOUNDARY: Final[str] = "__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__"
```

这是一个魔法字符串，插入在 system prompt 的 `list[str]` 中，标记**静态段**（所有用户共享，可全局缓存）与**动态段**（用户/会话特定）的切分点。

#### 3.3.2 两层作用

**Provider 层**（cache split 模块）：

```
Path A (use_global_cache_scope=True 且找到 BOUNDARY):
    [静态段...] BOUNDARY [动态段...]
    → Block1: 静态段 join → CacheScope.GLOBAL
    → Block2: 动态段 join → CacheScope.NONE

Path B (默认 / 找不到 BOUNDARY):
    [所有段 join] → CacheScope.ORG (单个 block)
```

**边界标记自身永远不出现在最终发送给 LLM 的文本中。** `split_sys_prompt_prefix` 用 `list.index()` 找到位置后丢弃它。

#### 3.3.3 为什么单独成文件

`boundary.py` 只有 3 行有效代码，但单独成文件是为了**避免 `builder.py` / `split.py` / `blocks.py` 之间的循环 import**。这是典型的"常量提取"模式。

### 3.4 Compaction 层 — `context/compact/`

#### 3.4.1 三层压缩策略

```
┌──────────────────────────────────────────────────────────────┐
│ L1: maybe_auto_compact                                       │
│     触发: 自动(上下文使用率 > 85%)                             │
│     行为: 估算 token → 找 boundary → 压缩 → 插入 boundary msg │
├──────────────────────────────────────────────────────────────┤
│ L2: maybe_microcompact_tool_results                          │
│     触发: 单个工具结果超过指定长度                             │
│     行为: 保留工具名 + 前 N 字符 + 尾部摘要                    │
├──────────────────────────────────────────────────────────────┤
│ L3: compact_now                                              │
│     触发: 用户主动执行 /compact 命令                           │
│     行为: force=True(跳过阈值), 压缩后清 Section 缓存           │
│           + MemoryLoader 缓存                                 │
└──────────────────────────────────────────────────────────────┘
```

#### 3.4.2 auto_compact 详细流程

[auto_compact.py:90-193](context/compact/auto_compact.py#L90-L193)：

```
maybe_auto_compact(messages, model, summarizer, ...)
  │
  ├─ 1. get_context_window_for_model(model)
  │      → 五级优先级推断上下文窗口大小(见 3.5 节)
  │
  ├─ 2. _estimate_messages_tokens(messages)
  │      → 粗略估算: role + kind + content 拼接后走 tiktoken
  │
  ├─ 3. 阈值检查: tokens_before < window * 0.85
  │      未达 → 返回 triggered=False (不压缩)
  │      force=True → 跳过检查(用户主动 /compact)
  │
  ├─ 4. find_last_compact_boundary(messages)
  │      → 找到最后一条 compact_boundary 消息的下标
  │      → 只压缩 boundary 之后的消息 (不重复压缩已压缩段)
  │
  ├─ 5. 保留最近 keep_recent_messages=6 条原始消息不动
  │      base_idx = last_boundary + 1
  │      upper_idx = max(base_idx, len(messages) - 6)
  │      to_summarize = messages[base_idx:upper_idx]
  │
  └─ 6. 三种摘要路径 (优先级降级):
        L1 → try_session_memory_summary(session_state)
              → 零 API 调用,直接用 SessionState.state_text()
        L2 → summarizer.summarize(to_summarize, focus=focus)
              → LLM 调用生成摘要 (可选注入)
        L3 → RuleBasedSummarizer.summarize()
              → 规则兜底: 取最近 12 条消息每条截 300 字符
```

#### 3.4.3 Compact Boundary Marker

[boundary.py:26-86](context/compact/boundary.py#L26-L86) 定义压缩边界标记：

```python
# 生成一条 role=user, kind=compact_boundary 的标记消息
def make_compact_boundary_message(*, summary, tokens_before, tokens_after, reason):
    return Message(
        role=MessageRole.USER,     # ← 关键: role 选 user 而非 assistant
        content=summary,           # LLM 当作普通 user 消息读到
        metadata={
            "kind": "compact_boundary",
            "tokens_before": tokens_before,   # LLM 不可见,仅供 TUI/日志
            "tokens_after": tokens_after,
            "reason": reason,
        },
    )
```

**为什么 role 选 `user` 而非 `assistant`？**
- 让模型把摘要当作"用户告诉我已经发生过的事实"
- 避免模型误以为摘要内容是它自己说过的话（防止 **self-conditioning 偏差**）
- Claude Code 源码中同样选择 `role=user`

**边界查找：**
```python
find_last_compact_boundary(messages) → Optional[int]   # 最后一条 boundary 的下标
messages_after_last_boundary(messages) → List[Message]  # boundary 之后的消息
is_compact_boundary(message) → bool                     # 判断是否为 boundary
```

#### 3.4.4 摘要器

`Summarizer` 协议（[summarizer.py:16-30](context/compact/summarizer.py#L16-L30)）：
```python
class Summarizer(Protocol):
    async def summarize(self, messages, *, focus=None) -> Optional[str]: ...
```

`RuleBasedSummarizer`（[summarizer.py:33-67](context/compact/summarizer.py#L33-L67)）：
- 不调 LLM，直接拼最近若干条 user/assistant 消息
- 默认参数：`max_messages=12`, `max_chars_per_msg=300`
- 作为 LLM 摘要不可用时的**兜底**

`try_session_memory_summary`（[session_memory_compact.py:15-41](context/compact/session_memory_compact.py#L15-L41)）：
- 从 `LocalSessionStore.state_text()` 提取摘要文本
- 零 API 调用，零成本
- 失败返回 None，由调用方降级到 LLM summarizer

#### 3.4.5 用户主动压缩

`compact_now`（[compact.py:28-56](context/compact/compact.py#L28-L56)）：
```python
async def compact_now(messages, *, model, summarizer, session_state, memory_loader, ...):
    result = await maybe_auto_compact(messages, ..., force=True, focus=focus)
    clear_system_prompt_sections()       # 清 Section 缓存
    memory_loader.reset_cache("user_compact")  # 清 Memory 缓存
    return result
```

即使 `triggered=False`（无可摘要内容），也清 Section cache 和 Memory cache，让用户下一轮至少看到 memory 重新加载的效果。

### 3.5 Budget 层 — `context/budget/`

#### 3.5.1 五级上下文窗口推断

[window.py:65-83](context/budget/window.py#L65-L83) 按优先级从高到低：

```
优先级 1: 环境变量 CB_AGENT_MAX_CONTEXT_TOKENS
          → 用户显式覆盖,最高优先级

优先级 2: model ID 含 "[1m]" / "[1M]" / "1m" 后缀
          → 正则 r"\[(?:1m|1M)\]|(?<![A-Za-z0-9])1[mM](?![A-Za-z0-9])"
          → 1,000,000 tokens

优先级 3: ConstantLLM.llm_dict[model]['max_input_tokens'] or ['max_tokens']
          → 项目自有的 LLM 注册表

优先级 4: betas 含 "context-1m-2025-08-07"
          → Anthropic 的 1M context beta header
          → 1,000,000 tokens

优先级 5: DEFAULT_CONTEXT_WINDOW = 200,000
          → 无任何信息时的保守默认值
```

#### 3.6.4 Provider 适配器模式

[provider_adapter.py](context/cache/provider_adapter.py) 定义协议和两种实现：

```python
class CacheControlAdapter(Protocol):
    def emit_system(self, blocks: Sequence[SystemPromptBlock]) -> Any: ...

class OpenAICompatibleAdapter:
    # OpenAI 兼容 API: blocks join 成单 string
    # scope 信息被丢弃(provider 不支持),但 Section LRU 缓存仍生效
    def emit_system(self, blocks) -> str:
        return "\n\n".join(b.text for b in blocks if b.text)

class AnthropicAdapter:
    # Anthropic 原生 API: 返回 list[dict] 带 cache_control
    # GLOBAL/ORG scope 的 block 打 cache_control={"type": "ephemeral"}
    def emit_system(self, blocks) -> List[dict]: ...
```

**设计收益（即使在 OpenAI 兼容路径下）：**
- Section LRU 缓存依旧避免重读 CLAUDE.md / 重算 env_info
- 调试 dump 仍可按 scope 着色
- 切回 Anthropic 直连时，session 端代码无需改动

## 七、关键设计决策与权衡

### 7.1 为什么 Section 用闭包而非配置字典？

每个 dynamic section 是一个**工厂函数返回 `SystemPromptSection`**，compute 是闭包，捕获构造时的依赖（loader / model / settings）。这样做的优势：
- 类型安全：`SystemPromptSection` 是 dataclass，IDE 可自动补全
- 延迟执行：Section 创建 ≠ compute 执行，resolve 阶段才真正跑
- 依赖隔离：每个 Section 只持有自己需要的引用，不会互相污染

代价：闭包序列化困难（但 Section 本身不需要序列化）。

### 7.2 为什么 boundary 选 user role？

LLM 将 `user` 消息视为外部事实，将 `assistant` 消息视为自己的产出。如果把压缩摘要标记为 `assistant`，模型可能认为"这是我之前说过的内容"从而产生 self-conditioning 偏差。标记为 `user` 则让模型将其视为外部提供的上下文事实。

### 7.3 为什么 Memory 从尾部截断？

`_enforce_total_char_limit` 从尾部（高优先级 = Local/Project cwd）向头部（低优先级 = Managed/远祖目录）累加，超出限制时截掉头部。这保证了离用户最近的指令始终保留，而远祖目录的通用指令在空间紧张时被丢弃——符合"越靠近 cwd 优先级越高"的直觉。

### 7.4 为什么 mcp_instructions 不可缓存？

MCP 服务可以在会话中动态 connect/disconnect。如果用缓存，connect 新服务后 system prompt 不会包含新服务的 instructions。`DANGEROUS_uncached_*` 命名和 `reason` 强制参数就是为了让未来的维护者清楚理解这个代价。

### 7.5 为什么 OpenAI 兼容路径仍保留 CacheScope 抽象？

虽然 OpenAI API 不支持 `cache_control`，但保留抽象的好处：
1. Section LRU 缓存照常生效（缓存发生在 list[str] 层，与 provider 无关）
2. 调试 dump 可以按 scope 着色区分静态/动态段
3. 切到 Anthropic 直连时只需换 adapter，上游零改动
4. 代码结构清晰表达了"哪些内容可以安全共享缓存"的意图

## 十、总结

这次重构将上下文工程从**单体流水线**转变为**六个可组合的模块**，每个模块职责清晰、可独立测试。核心的设计哲学是：

1. **延迟计算**：Section 创建与 compute 执行分离，resolve 阶段按需并发执行
2. **分层缓存**：Section LRU（进程内） + Provider cache_control（API 层）两级缓存
3. **优先级驱动**：Memory 从 Managed → Local 逐级覆盖、截断从低优先级开始
4. **适配器抽象**：CacheScope + ProviderAdapter 解耦业务逻辑与 API 格式
5. **安全降级**：压缩有 LLM → RuleBased 三级降级、token 计数有 tiktoken → 字符估算降级
