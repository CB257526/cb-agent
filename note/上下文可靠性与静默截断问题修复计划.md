# CbAgent 上下文可靠性与静默截断问题修复计划

## 1. 文档目标

本计划用于修复当前仓库中一组共同根因相近的问题：代码为了限制内存、控制上下文或
兼容异常路径，选择了静默截断、静默跳过、吞掉异常或把不同配置合并成一个全局值。
这些做法短期看起来可以让请求继续运行，长期却会造成以下结果：

- Agent 在没有明确 compact 的情况下丢失已提交对话或工具事实；
- provider 请求失败后仍提交一个不完整回合；
- 临时检索内容和重复工作状态不断堆积，导致过早 compact；
- 同名模型跨 provider 切换时使用错误的上下文窗口和能力配置；
- 工具声称可以分页读取完整结果，但原始结果其实已经永久丢失；
- 保护上限在单个超大对象面前失效，或者优先丢掉更重要的指令。

本次改造不引入新的 microcompact、history 窗口或消息级滑动淘汰。完整 active history
仍然是模型请求的事实来源；只有用户明确清空会话或一次正式 compact 成功安装
replacement history 时，才允许改变模型可见的历史前缀。

## 2. 必须遵守的系统不变量

后续实现和代码审查必须同时满足以下不变量。

### 2.1 对话历史不变量

1. 正式 active history 严格 append-only，不按消息数、字符数或固定 token 窗口裁剪旧
   history。包含 request-only context 的完整请求不要求跨用户回合整体 append-only。
2. 单条坏 transcript 记录不能让其它合法记录消失。
3. LLM 请求失败时，不得把当前 user-only 或半截 assistant 回合提交到正式 history。
4. 只有正式 compact 成功完成“摘要、replacement 校验、持久化”三个阶段后，才能替换
   active history。
5. UI 预览裁剪、日志裁剪与模型上下文裁剪必须是不同的数据副本，不能互相复用。

### 2.2 截断不变量

任何进入模型的工具结果、附件文本或外部数据，只能采用以下三种处理之一：

1. 内容完整且在预算内，直接发送；
2. 完整内容已经可靠持久化，发送有路径、大小、范围和续读方法的 preview；
3. 无法可靠持久化或继续分页时，明确拒绝本次操作并向用户报告，不能伪装成功。

禁止“截断后继续，但完整内容既不落盘也无法重新读取”。

### 2.3 动态上下文不变量

1. 动态 section 必须区分“读取成功且存在”“读取成功且确认不存在”“读取失败/未知”。
2. 读取失败不能被解释成 section 删除。
3. RAG knowledge、hook 指令、子代理运行通知等本轮临时内容不得进入长期 active history。
4. `state.json` 是 UI、审计和恢复辅助数据，不应重复总结已经存在于完整 history 中的
   工具调用和对话事实。

### 2.4 模型配置不变量

1. 运行时能力和窗口绑定具体 `ModelChoice.key`，不能只用 `model_id` 查找。
2. 同一个 `model_id` 可以在不同 provider 下具有不同窗口、输出上限和能力。
3. 模型降档判断、Footer、compact 预算和真实 provider 请求必须读取同一份运行时配置。

### 2.5 前缀缓存不变量

1. 同一用户回合的正常工具循环只能追加 assistant/tool/user runtime 消息，不回写旧消息。
2. 跨用户回合时，RAG、hook 等 request-only context 可以在上一轮动态尾部形成缓存断点；
   必须保持该插入点之前的 system + durable history 字节稳定。
3. 修复 transient context 时，不得通过“发送前过滤旧 history”持续改写已经提交的前缀。
4. 正式 compact 可以产生一次明确的前缀重置；compact 安装后的 durable history 重新保持
   append-only。
5. 工具 schema 使用稳定排序；相同模式和工具集合必须生成字节稳定的 schema。

## 3. 改造范围与非目标

### 3.1 本次改造范围

- `agent/work_context.py`：transcript、active turn、compact cursor 和恢复。
- `agent/cb_agents.py`：provider 异常传播、具体模型运行时配置。
- `agent/session.py`：错误事务、动态上下文分层、history 提交和自动 compact。
- `context/world_state.py`：section 三态与基线更新。
- `constant/llm/model_config.py`、`constant/llm/constant_llm.py`：模型配置真相来源。
- `agent/compaction.py`：超窗时的无丢失分段摘要。
- `tools/tools/bash_output.py`、`tools/tools/bash_tool.py`：完整输出持久化。
- `tools/tools/file_read_tool.py`：真正的流式分页读取。
- `context/memory/loader.py`：严格预算、优先级和显式缺失信息。
- `agent/multimodal_input.py`：附件 artifact 化和动态预算。
- 对应后端测试、RPC 事件和技术报告。

### 3.2 明确不改的合理保护

- UI、日志和事件面板可以保留有明确提示的 preview 裁剪；
- `file_read`、search、grep 等工具可以保留分页上限，但必须提供稳定续读游标；
- 单条 10K token、批量 40K token 的工具结果预算可以保留，前提是完整内容先落盘；
- 多模态 base64 继续禁止写入 history、transcript 和日志；
- transcript 继续保留完整审计，不因 compact 删除旧记录；
- 工具协议必须继续保证 assistant.tool_calls 与 tool 消息完整配对。

## 4. 第一阶段：修复 transcript 恢复的全量丢失

### 4.1 当前问题

`LocalSessionStore._read_transcript_items()` 在任意一行 JSON 解析失败后返回空列表。一条
尾部半写记录或人工损坏记录会让整个会话恢复为零条消息。当前 compact v2 又使用
`transcript_offset` 的有效列表下标；如果只简单跳过坏行，会让 offset 与物理文件行错位。

### 4.2 目标设计

引入稳定的 transcript cursor，并把物理读取结果与消息解析结果分开。

建议新增：

```python
@dataclass(frozen=True)
class TranscriptRecord:
    physical_line: int
    legacy_nonempty_ordinal: int
    turn_seq: int
    turn_id: str
    payload: dict[str, Any]

@dataclass(frozen=True)
class TranscriptReadResult:
    records: list[TranscriptRecord]
    corrupt_lines: list[int]
    trailing_partial_line: bool
```

实现要求：

1. transcript 每个新回合写入单调递增的 `turn_seq`；`turn_id` 继续用于幂等去重。
2. 逐行解析 JSONL。坏行记录行号并跳过，其它合法行继续恢复。
3. 最后一行没有换行且 JSON 不完整时标记 `trailing_partial_line=True`，不要影响之前记录。
4. 中间坏行必须写错误日志并在 session payload 中暴露恢复警告，不能静默忽略。
5. compact 快照升级为 v3，保存 `transcript_cursor_seq`，不再依赖解析后列表下标。
6. v2 的 `transcript_offset` 必须严格兼容当前 `_count_transcript_turns()` 语义：它表示
   “compact 当时 transcript 中非空物理行的数量”，不是过滤坏 JSON 后的有效记录数，也
   不是包含空行的原始文件行号。
7. 读取 v2 时逐物理行扫描：每遇到一条非空行就递增 `legacy_nonempty_ordinal`，即使该行
   JSON 已损坏也要占用序号；只回放 `legacy_nonempty_ordinal > transcript_offset` 的合法
   记录。禁止先过滤坏行再对 records 做 `records[offset:]`。
8. v2 快照只做上述兼容读取，不原地猜测或重写 offset；下一次成功 compact 再写成 v3。
9. 恢复时按 `turn_seq` 排序并按 `turn_id` 去重；重复记录保留最后一条完整记录。
10. transcript 追加后执行 `flush`；是否 `fsync` 做成配置，默认不强制，避免每轮明显变慢。

### 4.3 写入事务

正式回合提交顺序保持：

```text
pending_user / active_turn
    -> append transcript 完整 JSON 行
    -> flush
    -> 更新 state/index
    -> 删除 active_turn 与 pending_user
```

若 transcript 追加失败，不得清理 active turn。若 state/index 更新失败，transcript 已经是事实
来源，重启时按 `turn_id` 去重恢复。

### 4.4 测试

- 合法行 + 损坏尾行：恢复所有合法历史；
- 合法行 + 损坏中间行 + 合法行：恢复前后两段并返回 corruption warning；
- v2 offset 遇到 offset 前坏行、offset 后坏行和空行：都不会重复或漏掉 compact 之后的
  合法回合；
- 断言 v2 兼容路径按 `legacy_nonempty_ordinal` 选择，而不是按有效 records 下标选择；
- v3 cursor 遇到删行、空行和重复 turn_id：恢复结果稳定；
- transcript 成功、state 写失败：重启仍恢复回合；
- transcript 写失败：active turn 保留且正式 history 不推进。

## 5. 第二阶段：让 provider 错误进入正常事务控制

### 5.1 当前问题

`CbAgentsLLM.think()` 捕获所有异常后返回 `None`。Session 无法区分 context overflow、
限流、鉴权失败、网络错误和代码错误，最后还会提交当前 user-only 回合。

### 5.2 目标设计

新增统一异常层：

```python
class LLMRequestError(RuntimeError): ...
class LLMContextOverflowError(LLMRequestError): ...
class LLMRateLimitError(LLMRequestError): ...
class LLMAuthenticationError(LLMRequestError): ...
class LLMTransportError(LLMRequestError): ...
class LLMInvalidRequestError(LLMRequestError): ...
```

异常对象至少包含：

- provider、model key、model id；
- HTTP status 和 provider request id；
- 是否允许重试；
- 原始异常类型；
- 已脱敏的错误文本；
- 当前 `round_idx`。

`CbAgentsLLM.think()` 只负责分类并抛出，不再返回 `None` 表示失败。流式中途失败时还要
携带已经收到的正文和 reasoning 是否完整，禁止把半截 tool_calls 当成正式结果。

错误分类采用“结构化证据优先、文本启发式保守兜底”：

1. 优先读取 SDK 异常类型、HTTP status、provider error code/type 和结构化响应字段；
2. 只有明确的 `context_length_exceeded`、`prompt_too_long`、input/context token exceeded
   等标记才能自动分类为 overflow；
3. 禁止把裸 `max_tokens`、`token`、HTTP 400 或 `invalid request` 单独作为 overflow 证据，
   因为它们也可能表示输出参数不兼容、字段错误或模型不支持；
4. provider 文案不明确时归入 `LLMInvalidRequestError` 或未知 `LLMRequestError`，不自动
   compact、不自动重试；
5. provider 特有规则放进独立 adapter/registry 并配套正反例测试，不继续扩张一个全局
   字符串 marker 列表。

### 5.3 Session 处理规则

- `LLMContextOverflowError`：若本轮尚未自动 compact，执行一次正式 compact、重建请求并
  重试；已经重试过则停止并保留 active checkpoint。
- `LLMRateLimitError`：遵守 provider 的 retry-after；只允许有界重试，不提交失败回合。
- 鉴权和 invalid request：立即失败，不自动重复请求。
- 网络错误：允许配置化的一次幂等重试；流式已经产生可见正文时不得自动重复，避免用户
  看到重复文本。
- 任何最终失败：发出结构化 Error/Done，保留 pending/active turn，不调用 `append_turn()`，
  不推进 World State baseline，不累计一个空 assistant 回合。

### 5.4 测试

- provider 400/401/429/5xx/timeout 分别映射正确异常；
- `max_tokens` 参数不支持、输出上限错误、配额不足等包含 token 字样的错误不得误判为
  context overflow；
- 未知 400 不触发 compact 或自动重试；
- context overflow 只 compact 并重试一次；
- provider 失败后 history、transcript、baseline 均不变；
- 流式输出一半后断开，不产生半截 tool_calls；
- 用户显式重试时复用 pending turn_id，不重复落盘用户消息；
- Footer usage 只累计 provider 确认返回 usage 的请求。

## 6. 第三阶段：模型配置改为按具体 ModelChoice 生效

### 6.1 当前问题

`ModelConfigManager` 允许不同 provider 使用相同 `model_id`，但又把能力写入全局
`ConstantLLM.llm_dict[model_id]`。最后加载的同名配置覆盖前面的配置。模型预览、切换、
Context Footer 和降档 compact 因而可能读取错误窗口。

### 6.2 目标设计

新增不可变运行时配置：

```python
@dataclass(frozen=True)
class ActiveModelConfig:
    key: str
    provider_key: str
    provider_name: str
    model_id: str
    base_url: str
    max_context_tokens: int
    max_output_tokens: int
    output_token_param: str
    is_tool: bool
    is_reasoning: bool
    image_ability: bool
```

`CbAgentsLLM` 持有 `active_model_config`，以下逻辑全部读取它：

- `AgentSession._model_max_tokens()`；
- soft/hard limit；
- `max_output_tokens` 请求参数；
- Function Calling、reasoning 和 image 能力；
- model downshift 预览与 compact replacement 预算；
- Footer 和 `session.model` RPC payload；
- token calibration key。

`ConstantLLM.llm_dict` 只保留内建默认能力，不再被外部 models.json 以 `model_id` 全局覆盖。

### 6.3 环境变量兼容决策

- 没有 models.json、仅使用旧环境配置时，`MAX_TOKENS`、`MAX_OUTPUT_TOKENS` 等继续生效；
- 使用 models.json 时，每个 `ModelChoice` 自己的字段优先，旧全局 `MAX_TOKENS` 不再覆盖
  所有可切换模型；
- 如确实需要全局强制覆盖，新增语义明确的 `CBAGENT_FORCE_MAX_CONTEXT_TOKENS`，并在 UI
  显示“全局覆盖已启用”；
- 启动时发现同名 model id 时允许存在，但日志和 UI 必须使用唯一 provider key 区分。

### 6.4 测试

- 两个 provider 使用同一 model id、不同窗口，切换后各自值正确；
- 大窗口同名模型切到小窗口同名模型时仍触发 downshift compact；
- env-only 旧配置兼容；
- models.json 与强制全局覆盖的优先级清晰；
- 切换失败后完整恢复旧 client、active config 和环境兼容字段；
- token 校准按 provider key + model key 隔离。

## 7. 第四阶段：动态上下文三态化并分离 transient history

### 7.1 当前问题

当前 dynamic context 发生异常时回退成空列表，World State 把它解释成全部删除。同时
`knowledge` 和 runtime instructions 虽然不进入 baseline，却与持久 section 共用同一条
`context_update`，最终还是写进完整 history。

### 7.2 数据结构

```python
@dataclass(frozen=True)
class DynamicSectionResult:
    name: str
    status: Literal["present", "absent", "error"]
    text: str = ""
    error: str = ""
    persistence: Literal["persistent", "request_only"] = "persistent"
```

`persistence` 是唯一分流依据。禁止在 Session 中继续通过 section 名、字符串标签、role 或
正则表达式推断一条消息是否应该持久化。

规则：

- `present`：与 baseline 比较，变化时追加新值；
- `absent`：只有 section 的读取过程成功且确认不存在时，才能生成 removed；
- `error`：沿用 baseline，不生成更新或删除；关键 section 无 baseline 时阻止请求；
- `request_only`：只加入当前请求，不写入 `turn_prefix_messages`、history 或 compact baseline。

### 7.3 关键 section 的失败策略

- instructions：有 baseline 时沿用；首轮无 baseline 时读取失败则中止请求；
- environment/current date/language：有 baseline 时沿用，失败只记录 warning；
- MCP instructions：连接状态明确且服务已移除时才 absent，连接异常时 error；
- knowledge：失败时本轮不注入，但不得影响长期 baseline；
- plan：PlanStateStore 读取失败时沿用 baseline，不能自动切回 execute 语义；
- runtime hook instructions：仅当前请求有效，失败不持久化。

### 7.4 统一 request-only 通道

knowledge、hook runtime instructions 和子代理运行通知全部走同一套 request-only 通道。
`session_state` 默认不进入模型请求。PlanState 仍是持久、权威的动态 section，但不再依赖
`_strip_plan_sections_from_context_update()` 这种发送前正则改写特例。

建议让请求组装结果显式携带持久化语义：

```python
@dataclass
class RequestAssembly:
    provider_messages: list[dict[str, Any]]
    durable_turn_prefix: list[Message]
    request_only_audit: list[dict[str, Any]]
```

运行时注入函数只能向 `provider_messages` 和 `request_only_audit` 添加内容，不能让
`_extract_protocol_messages()` 仅凭 `role=user` 把它们收进 history。provider 请求前应由
统一序列化层剥离本地持久化元数据，禁止把私有字段发送给 OpenAI-compatible provider。

旧版 Plan context 的 strip 逻辑只允许在一次性加载/迁移边界运行，并产出规范 Message；
不能在每次 `_sliced_history_dicts()` 时重新改写请求副本。迁移完成后删除该正则特例，避免
knowledge、hook、subagent 后续各自再长出一套过滤逻辑。

### 7.5 请求与提交结构

一次请求按以下顺序构造：

```text
稳定 system
完整 active history
持久 section 增量 context_update（可能为空）
本轮 request-only context（RAG/hook/subagent update）
当前用户消息
```

回合成功后只把以下内容提交 history：

```text
持久 section 增量 context_update
用户消息
assistant/tool 协议链
```

request-only context 可以写入 transcript 的 `ephemeral_context_audit` 字段用于排障，但该字段
不得由 `load_latest_history()` 还原成模型消息。崩溃恢复时根据 pending user query 重新执行
RAG，不复用可能已经过期的旧检索结果。

### 7.6 SessionState 去重

`state.json` 继续维护文件、命令、决策和待办，供 UI、会话列表和人工审计使用，但健康
会话不再把 `session_state` 每轮注入模型，因为完整 history 已包含原始事实。

只有以下情况允许生成一次 `recovery_context`：

- transcript 不可用但 state.json 可用；
- 从旧版会话迁移且缺少完整协议历史；
- 用户显式调用诊断/恢复命令。

`recovery_context` 必须标注来源和缺失范围，只追加一次，不随 state 每轮重复。

### 7.7 缓存迁移要求

已有 history 中已经提交的 knowledge/context_update 不在发送前动态删除。这样做会回写历史
前缀并造成新的 cache miss。旧 transient 内容等待下一次正式 compact 自然被 summary 接管；
新版本只保证不再新增错误的持久消息。

request-only context 不可能同时满足“下一轮删除旧内容”和“完整请求前缀完全不变”。正确的
缓存预期是：

```text
上一轮：system + durable_history_N + RAG_N + user_N
下一轮：system + durable_history_N + user_N + assistant_N + RAG_N+1 + user_N+1
共同前缀：system + durable_history_N
```

因此下一轮允许重新 prefill 最近一轮的动态尾部，但更早的 durable history 必须继续命中
缓存。该取舍用有限的最近一轮 cache miss，换取旧 RAG 不长期占用上下文、不污染后续语义，
并减少因无效累积导致的提前 compact。不得为了提高短期 cache hit 把所有原始 RAG 永久
写入 history；真正需要跨轮保留的内容只保存 citation、artifact 路径或短事实摘要。

### 7.8 测试

- instructions 读取失败时沿用 baseline，不发送 removed；
- 首轮 instructions 失败时请求不发送；
- knowledge 每轮可变化，但成功回合后不在 active history 中；
- hook 和 subagent request-only 消息同样不进入 active history；
- PlanState 不依赖发送前 regex strip，旧版 plan 只在迁移边界规范化一次；
- transcript 审计可以看到 ephemeral 元数据，恢复 history 看不到；
- SessionState 更新不会增加模型请求 token；
- 同一工具回合的连续请求保持严格 append-only；
- 跨用户回合移除 request-only context 时，缓存断点不早于上一轮 transient 插入位置；
- section 真正删除时只追加一次 removed。

## 8. 第五阶段：compact 超窗改为无丢失分段归并

### 8.1 当前问题

当一次摘要请求超过 hard limit 时，当前实现从最旧协议段开始删除，再让模型摘要剩余历史。
被删除的内容没有被任何摘要模型读取，最终 handoff 不可能保留其中事实。

### 8.2 目标算法

正常 soft-limit compact 仍优先执行一次完整结构化摘要。只有摘要输入无法装入当前摘要模型
时，才启用分段归并：

1. 按真实 user 回合拆分结构化历史，保持 tool call/result 配对。
2. 从最旧回合开始组装尽可能大的 chunk，每个 chunk 加摘要指令后不超过 hard limit。
3. 对每个 chunk 生成结构化局部 handoff，并记录该 chunk 覆盖的消息范围和摘要 usage。
4. 将局部 handoff 作为结构化 summary 消息，与尚未处理的后续回合继续归并。
5. 若局部 summaries 仍无法一次放入窗口，递归执行 reduce，直到得到唯一最终 handoff。
6. 最终 replacement 继续保留动态预算计算出的最近完整原始回合。

必须提供一个可测试的不变量：compact source 中每条消息都至少出现在一个摘要请求的
`messages` 中，不能只存在于 transcript 审计而未被摘要模型看见。

### 8.3 成本和递归上限

hierarchical compact 必须是有界操作，不能为了“不丢消息”无限调用模型。默认限制建议为：

```text
max_chunks = 8
max_summary_requests = 12
max_total_prompt_tokens = 4 * summary_model_hard_limit
max_total_completion_tokens = min(64K, 4 * summary_model_max_output_tokens)
```

这些值允许按模型配置覆盖，但不能设置成无上限。执行器在每次 provider 调用前使用校准估算
预扣预算，provider usage 返回后再用实际值结算；provider 不返回 usage 时继续使用保守估算。
初始 single-pass 请求如果只做本地估算且没有真正发送，不计入 `summary_requests`，实际发出的
map/reduce 请求全部计入。

命中任意 chunk、请求轮次、累计 prompt token 或累计 completion token 上限时：

- 立即终止本次 compact；
- 抛出包含已用预算和命中上限的 `CompactionBudgetExceeded`；
- 不安装局部 summary，不替换 history，不推进 transcript cursor 或 world state；
- 不允许退化为丢最旧消息、规则摘要或裁剪用户正文；
- 已生成的局部 summary 只作为审计记录，不得在下一轮冒充正式 handoff。

### 8.4 单条超大消息

- tool result：按工具结果不变量，应该已经有完整 artifact 路径；摘要请求使用 preview +
  artifact 元数据，不再裁剪未知正文；
- 附件文本：使用附件 artifact 引用；
- 真实用户消息或 assistant 正文单条仍超过摘要窗口：compact 明确失败并提示创建新会话或
  使用更大窗口模型，禁止静默砍掉正文；
- 任何失败都不替换现有 history。

### 8.5 持久化与审计

compact v3 增加：

- `strategy`: `single_pass` 或 `hierarchical`；
- `summary_requests`、`summary_prompt_tokens`、`summary_output_tokens`；
- `max_chunks`、`max_summary_requests` 和最终命中的预算状态；
- `source_message_count`、`covered_message_count`；
- `transcript_cursor_seq`；
- `target_model_key`，不能只保存 model id。

删除或废弃 `dropped_compact_messages`，因为新算法不允许“未摘要直接丢弃”。

### 8.6 测试

- history 小于 hard limit 时只调用一次摘要；
- 3 倍窗口历史触发 map/reduce，所有唯一 marker 都进入至少一个请求；
- chunk、请求数、累计 prompt 和累计 completion 四种上限分别命中时均事务失败；
- 超限失败后 history、compact snapshot、cursor 和 baseline 完全不变；
- 工具调用配对在每个 chunk 中合法；
- 单条不可恢复超大用户消息导致 compact 失败且 history 不变；
- 连续多次 hierarchical compact 后仍保留上一 handoff；
- 模型降档按旧模型生成摘要、按目标模型计算 replacement；
- transcript cursor 与 mid-turn 提交无重复。

## 9. 第六阶段：统一 Bash 输出的“先保存、后预览”

### 9.1 快速正确性修复

在不立即重写进程执行器的前提下，先统一阈值：

这一小节是后续 file_read 分页和 artifact 方案的前置提交，必须先落地。不能等 spool 重构
一起完成，因为当前 100K 到 1MiB stdout 和 20K 以上 stderr 已经存在永久丢失区间。

- stdout 或 stderr 只要触发模型可见截断，就先分别落盘完整原文；
- 返回 `stdout_file`、`stderr_file`，保留旧 `output_file` 作为 stdout 兼容别名；
- preview 中提供原始字符数、字节数、行数和 file_read 续读示例；
- result cap 检测到已有文件路径时不得重复持久化已经截断的 JSON；
- 持久化失败时工具返回明确错误，不能返回一个看似成功但不可恢复的截断结果。

### 9.2 后续流式实现

把 `Popen.communicate()` 全量收集改为边读边写 spool 文件：

1. stdout/stderr 分别使用有界内存 ring buffer 保存 preview；
2. 完整流持续写临时文件；
3. 进程完成后原子 rename 为正式 artifact；
4. 未触发截断的小输出可删除临时文件；
5. 超过硬上限时停止进程并返回明确的 hard-limit 错误，不伪称已经保存完整输出；
6. cancel/timeout 路径也要关闭文件并保留已经产生的部分输出。

### 9.3 测试

- 100K 以下完整返回且无需 artifact；
- 100K 到 1MiB stdout：截断 preview，但完整文件可读；
- 20K 以上 stderr：完整 stderr 文件可读；
- stdout/stderr 同时超限，路径互不覆盖；
- result cap 后路径仍指向原始完整输出；
- cancel、timeout、持久化失败和硬上限行为明确。

## 10. 第七阶段：让 file_read 真正分页

### 10.1 当前问题

当前 `file_read` 先 `read_text()` 和 `splitlines()` 整个文件，再返回 head/tail/range。即使只读
前 100 行，也可能为一个超大日志分配多份完整内存。

### 10.2 模式化读取

- head：按行迭代，读够 N 行或输出预算即停止；
- range：流式跳过到 start_line，再读取目标范围；
- tail：使用反向分块读取或有界 deque，不保存全部行；
- char_range：使用增量解码器流式跳过字符，不能一次加载全文；
- 新增 byte_range：读取工具 artifact 时优先使用字节范围，游标更稳定；
- 所有模式返回 `has_more`、`next_start_line` 或 `next_start_byte`；
- 不为了计算 `total_lines`、`total_chars` 再扫描整个文件。无法廉价获得时返回 `null`，
  同时提供文件总字节数。

读取状态登记继续保存 path + mtime；FileEdit 的 stale check 不受影响。

### 10.3 测试

- 使用受控 file object 断言 head 模式没有读取文件尾；
- 多 GB 稀疏文件读取 head 时内存保持有界；
- range/tail/char_range/byte_range 的边界和 UTF-8 跨块解码正确；
- continuation cursor 能无重复、无缺口遍历文件；
- 文件读取过程中被修改时返回 staleness warning。

## 11. 第八阶段：修复 Memory 指令预算

### 11.1 优先级规则

Memory 文件不能简单按列表尾部截断。建议固定优先级：

1. Managed 安全与组织指令，必须保留；
2. User/Global 用户级指令；
3. 当前 cwd 最近层级的 Project 指令；
4. Local/ShortTerm 工作记忆；
5. 远祖目录 Project 指令。

“更靠近 cwd”影响同一层级内部顺序，但不能让一个超大 Local 文件挤掉 Managed 指令。

### 11.2 严格预算

- 总字符/token 预算必须包含 formatter 的标题和路径开销；
- 单个文件大于其预算时，不再直接完整纳入；
- instruction 文件不允许无提示截断。返回 manifest，明确列出 omitted/truncated 文件和路径；
- Managed 指令无法完整容纳时应阻止请求并要求拆分，而不是只取前半段；
- 普通 ShortTerm/Memory 内容可先完整落盘，然后注入有来源的摘要或 preview；
- 256KB 单文件保护不能发生在 `@include` 解析之前。超大文件应明确报错，或使用流式扫描
  解析 include，不能让文件尾部 include 静默消失。

### 11.3 测试

- 单个 50K Local 文件不会突破 40K 总预算；
- 超大 Local 不会挤掉 Managed/User 指令；
- formatter 开销计入预算；
- 被省略文件在模型可见 manifest 和日志中均可定位；
- include 位于 256KB 之后时不会静默丢失；
- Memory 文件临时读取失败时走 dynamic section 的 error 语义，不发送 removed。

## 12. 第九阶段：附件 artifact 化与聚合预算

### 12.1 文本和文档附件

文档转换后的完整 Markdown 写入：

```text
.cbagent/attachments/<content_hash>/content.md
```

当前请求只注入：

- 文件名、原始路径、类型、hash 和原始大小；
- 转换后 artifact 路径和字符/token 数；
- 根据当前模型窗口动态计算的 preview；
- 使用 file_read 分页读取其余内容的明确提示。

history 只保存附件 manifest 和用户原始文字，不保存固定 120K 字符正文。若任务确实需要
全文，Agent 应通过 file_read 分段读取，工具结果按现有持久化规则进入 history。

### 12.2 聚合预算

- 附件总预算按当前 soft limit 的比例计算，并设置合理上下界；
- 预算作用于所有附件之和，不是每个附件各拿 120K；
- 当前用户文字、system、tools 和已有 history 先计入，再分配剩余附件预算；
- 多附件超过预算时仍全部生成 manifest，但只为高优先级附件提供 preview；
- 原生图片不能按 base64 字符数估算，应使用 provider/model 可配置的视觉 token 估算；
- 请求前检查附件数量、单文件大小和聚合视觉预算。

### 12.3 测试

- 200K 文档尾部内容可通过 artifact 分页读取；
- history 不包含 120K Markdown 正文；
- 多附件总 preview 不超过聚合预算；
- 转换失败、artifact 写失败时请求明确失败；
- 图片 base64 不进入日志、history、transcript 或 token JSON 序列化估算；
- 小窗口模型收到大附件时不会尝试用 compact 历史解决当前输入超窗。

## 13. 第十阶段：清理误导接口和过期文档

这一阶段不是重新实现 history 窗口。active history 当前已经不按消息数裁剪，且已有
`test_history_window_no_longer_cuts_*`、`test_history_window_no_longer_truncates_*` 回归测试。
执行者必须保留“全量 active history”行为，只删除已经无效的兼容入口和误导文档。

完成上述改造后删除以下遗留内容：

- `AgentSession.history_window` 构造参数和成员；
- 子代理创建时传入的 `history_window=8`；
- `load_latest_history(max_messages=...)` 的生产接口；测试如果需要裁剪，应调用独立测试 helper；
- `_trim_restored_history()` 及只为窗口截断服务的文档；
- `_build_chat_messages()` 中“切片+窗口截断”的过期说明；
- `dropped_compact_messages` 和 compact 删除最老回合的说明；
- “SessionState 每轮注入模型”的旧技术报告；
- `MAX_STDOUT_CHARS` 与 1MiB 落盘阈值相互独立的旧说明；
- 固定 120K 附件正文注入说明。

保留孤儿 tool 消息检测，但将其定位为存储损坏防御，而不是正常窗口截断后的补救机制。
如果正常 active history 出现孤儿消息，应该记录高等级错误，而不是只写 info。

清理后的测试应重命名为“默认恢复完整 history”和“replacement history 不裁剪”等正向
语义，不能删除这些回归保障，也不能借清理之名重新引入新的窗口参数。

## 14. 实施顺序与提交拆分

建议按以下顺序实施，每一步单独提交并保持测试可运行：

1. `transcript: salvage corrupt jsonl records and add stable cursor`
2. `llm: propagate typed provider errors without committing failed turns`
3. `models: bind runtime limits and capabilities to model choice key`
4. `context: add tri-state sections and request-only context`
5. `context: remove duplicated session state injection`
6. `compact: replace unseen-message dropping with hierarchical summaries`
7. `bash: persist every truncated stdout and stderr result`
8. `file-read: stream paginated reads with continuation cursors`
9. `memory: enforce strict prioritized instruction budgets`
10. `attachments: persist converted artifacts and apply aggregate budgets`
11. `cleanup: remove history window compatibility paths and rewrite reports`

不要把所有改动压进一个提交。前四步改变基础事务和配置真相来源，后续工具与 compact
改造依赖这些语义，拆分后更容易定位回归。

## 15. 总体测试矩阵

### 15.1 历史与恢复

- 正常多轮、工具多调用、并行工具、取消和异常退出；
- transcript 尾行/中间行损坏；
- pending + active + transcript 去重；
- compact v2 读取和 v3 写入；
- 会话切换和进程重启；
- 任何正常请求都不按消息数裁剪 history。

### 15.2 缓存稳定性

- 同一用户回合的连续工具请求满足上一轮规范请求是下一轮请求的严格前缀；
- 跨用户回合时，RAG、hook 和子代理通知只存在于对应请求，不修改 durable history；
- 移除上一轮 request-only context 后允许最近动态尾部 cache miss，但共同前缀必须至少覆盖
  system + 该 transient 插入前的完整 durable history；
- 未触发 compact 时 durable system/history/tools schema 字节稳定；
- 触发 compact 时只在 replacement 安装点发生一次前缀变化；
- 模型切换视为明确 cache boundary，不伪装成同一缓存命中链。

### 15.3 上下文与模型切换

- 128K、400K、1M 和极小测试窗口；
- 同 model id 不同 provider/window；
- 大模型切小模型自动 compact；
- provider 实际 overflow 后的补偿 compact；
- compact 单次、分段和递归 reduce；
- hierarchical compact 的 chunk/request/token 成本上限；
- 所有 source message coverage 为 100%。

### 15.4 工具与附件

- 单条/批量工具结果 cap；
- Bash stdout/stderr 各个阈值；
- file_read 所有分页模式；
- 文本、文档、图片和音频附件；
- artifact 写失败和续读；
- 多附件聚合预算。

### 15.5 动态上下文

- section present/absent/error 三态；
- instructions 首轮失败与已有 baseline 失败；
- RAG 不持久化；
- Plan/MCP/环境真实变更和临时读取失败；
- SessionState 不再重复占用模型 token。

## 16. 可量化验收标准

全部满足后才算完成：

1. 任意单行 transcript 损坏不会让其它合法回合消失。
2. 所有 provider 失败路径均不会新增正式 history 或 transcript 回合。
3. 同名模型跨 provider 的窗口和能力测试全部通过。
4. 动态 section 读取失败不会生成 removed 更新。
5. 连续 20 轮 RAG 请求后，active history 中没有 knowledge context_update 累积。
6. SessionState 更新不会增加下一轮请求 token，除非进入明确 recovery 模式。
7. hierarchical compact 的 source message coverage 为 100%，不存在 dropped unseen message。
   同时 chunk、摘要请求、累计 prompt 和累计 completion 均有硬上限；任一超限时 history
   和 compact snapshot 不变。
8. 任何被截断的 Bash/附件结果都有可读的完整 artifact；持久化失败则操作失败。
9. `file_read(head=100)` 对超大文件保持有界内存，不读取完整文件正文。
10. Memory 注入严格不超过预算，Managed/User 指令不会被 Local 文件挤掉。
11. 同一工具回合的连续请求保持严格 append-only；跨用户回合的规范 JSON 共同前缀必须
    精确截止到上一轮 request-only context 的插入位置，不能更早失效。
12. 仓库运行时代码中不再存在 `history_window`、生产 `max_messages` 恢复裁剪和
    `dropped_compact_messages`。
13. v2 compact 快照按非空物理行序号兼容回放；坏 JSON 行不会改变 offset 后合法回合的
    选择结果。
14. 未知 provider 400 和仅包含 `max_tokens` 的错误不会触发自动 compact 或自动重试。
15. knowledge、hook、subagent 通知共用 request-only 通道，Plan 不依赖发送前 regex strip，
    `session_state` 默认不注入。

## 17. 执行者禁止采用的捷径

- 不得新增固定最近 N 条消息、最近 N 轮或最近 N 字符作为 active history；
- 不得在发送请求前原地缩短已经进入 history 的旧 tool result；
- 不得用规则摘要兜底替代失败的正式 compact；
- 不得把 provider 异常转换成空字符串、空列表或 `None` 后继续提交；
- 不得把读取异常转换成 section absent；
- 不得为了兼容同名模型继续把 provider 配置写回全局 model-id 表；
- 不得只添加“已截断”提示而不提供完整 artifact 或明确失败；
- 不得通过扫描并改写旧 context_update 来迁移 transient 内容；
- 不得以测试只验证消息数量为由忽略协议配对、内容覆盖率和前缀字节稳定性。
- 不得把已经全量工作的 active history 当成待修逻辑；清理 `history_window` 只能删除死字段、
  子代理死参数和生产 `max_messages` 裁剪入口。
- 不得让 hierarchical compact 无界递归或无界调用 provider；命中预算必须事务失败。
- 不得把 v2 `transcript_offset` 解释成过滤坏行后的 records 下标。
- 不得用宽泛文本 marker 把未知 provider 错误猜成 overflow。
- 不得在 Bash 完整落盘语义修复前宣称 file_read 分页已经解决输出丢失。
- 不得为 knowledge、hook、subagent 和 Plan 分别增加新的字符串/正则过滤特例。
