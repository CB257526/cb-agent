# 项目级会话隔离实现思路

## 1. 背景

cb-agent 现在同时支持三类交互入口：

- CLI：用户在命令行里直接输入；
- TUI：Ink/React 终端界面，通过 JSON-RPC 网关和后端通信；
- 通讯平台：QQ/NapCat 已落地，未来还会接微信等 IM 平台。

这三类入口对“会话隔离”的要求不完全一样：

- CLI/TUI 需要用户主动创建、切换、清理本地 session，把不同任务拆开；
- QQ/微信需要自动按群聊、好友私聊隔离上下文，避免 A 群内容串到 B 群；
- EventBus、todo、ask_user_question、文件发送等工具事件必须能回到正确会话；
- history、state、transcript、compact 这些长期上下文不能跨会话混写。

因此项目里的会话隔离不是单点功能，而是一套分层机制：本地 session 解决“同一个前端里的多任务切换”，通讯平台 session 解决“不同外部会话自动隔离”。

## 2. 核心原则

项目级会话隔离遵守几个原则：

1. 隔离边界放在 `AgentSession + LocalSessionStore`。
   每个独立会话都有自己的 `AgentSession.history` 和自己的 `LocalSessionStore` 根目录。

2. 长期上下文只写当前会话目录。
   `transcript.jsonl`、`state.json`、`compact.json`、`compactions.jsonl` 都跟随当前 store 写入，避免跨目录落盘。

3. 前端显示不是隔离边界。
   TUI 面板、QQ 消息、CLI 输出都只是不同 renderer；真正决定上下文归属的是后端 session/store。

4. 事件流必须有会话路由。
   EventBus 事件本身不带会话 ID，因此通讯平台并发场景用 `ContextVar` 绑定当前 `ConversationKey`。

5. 工具状态也要审计。
   只隔离 AgentSession 不够；像 `todo` 这种全局工具实例内部还有状态，也必须按平台会话拆分。

## 3. 本地 CLI/TUI 多会话

CLI/TUI 的多会话以项目目录下的 `.cbagent/sessions/` 为根：

```text
.cbagent/
  sessions/
    index.json
    session_20260602_120000_ab12cd34/
      transcript.jsonl
      state.json
      compact.json
      compactions.jsonl
    session_20260602_130000_ef56ab78/
      transcript.jsonl
      state.json
```

`LocalSessionStore` 负责：

- `list_sessions()`：扫描 `session_*` 目录，返回轻量摘要；
- `create_session()`：创建新的空 session，并把它写入 `index.json` 作为 active；
- `switch_session(session_id)`：切换 active 指针，并加载目标 session 的 state；
- `load_latest_history()`：从目标 session 恢复普通 user/assistant history 和工作记录；
- `append_turn()`：把本轮 user/final/work_record 写入当前 active session；
- `save_compaction()`：把 compact 快照写入当前 active session。

`AgentSession.create_session()` 会清空内存 `history`，然后使用新的 active store。`AgentSession.switch_session()` 会切换 store 的 active 指针，再重新加载目标会话 history。这样 TUI 切换会话时，后端上下文和前端显示会一起替换，不会把旧会话继续带进新请求。

TUI/JSON-RPC 层还有一个重要保护：busy 时拒绝 `session.create` 和 `session.switch`。如果模型正在响应时强行切换 active session，可能出现“用 A 会话上下文推理，却把结果写进 B 会话目录”的竞态，所以网关必须拦住。

## 4. 通讯平台会话隔离

通讯平台不能让用户手动 `/switch`，因为群聊和好友私聊天然就是不同会话。平台层使用统一的 `ConversationKey` 做隔离键：

```python
ConversationKey(platform="qq", kind="group", id="123456")
ConversationKey(platform="qq", kind="private", id="10001")
ConversationKey(platform="wechat", kind="group", id="roomid_xxx")
ConversationKey(platform="wechat", kind="private", id="wxid_xxx")
```

稳定字符串形式为：

```text
<platform>:<kind>:<id>
```

例如：

```text
qq:group:123456
qq:private:10001
wechat:group:roomid_xxx
```

`AgentRunner.get_or_create_platform_session(conversation)` 保留这个名字是为了兼容平台适配器注入点，但现在的语义是“为当前消息创建一个短生命周期 `AgentSession`”。它复用全局 LLM、工具注册表、MCP、EventBus 和 ToolExecutor，只隔离会话对象与可选的本地存储。

私聊会挂载按好友 ID 隔离的本地存储目录：

```text
.cbagent/
  platform_sessions/
    qq/
      private_10001/
        sessions/
    wechat/
      private_wxid_xxx/
        sessions/
```

私聊会话有自己的：

- `AgentSession.history`；
- `LocalSessionStore`；
- `transcript.jsonl`；
- `state.json`；
- `compact.json`；
- messages 日志文件；

群聊默认不挂 `LocalSessionStore`，也就不写 `transcript.jsonl/state.json/compact.json`。这样可以避免大群高频消息把本地上下文和磁盘文件无限撑大。群聊仍会拿到临时 `AgentSession.history`，但处理完该消息后对象释放，历史随之丢弃。

这意味着 QQ 私聊用户 C、未来微信好友 D 不会共享长期上下文；QQ 群聊 A/B 不会共享运行态，但默认也不会形成长期磁盘上下文。

## 5. 同一会话串行，不同会话并发

通讯平台适配器内部维护按会话拆分的轻量队列状态：

```text
_conversation_queues[conversation.stable_id] = {
  lock,
  pending
}
```

同一个 `ConversationKey` 如果已经在运行，后续消息会在该会话队列里等待，而不是直接拒绝：

```text
好友 A 消息 1 -> 好友 A 消息 2 串行
群聊 X 消息 1 -> 群聊 X 消息 2 串行
```

这样可以避免两条私聊消息同时写同一个 `history/state/transcript`，也能让用户连续发送多条消息时自然按顺序处理。

不同 `ConversationKey` 可以并发运行。比如：

- QQ 群 `10001` 正在跑长任务；
- QQ 私聊 `20002` 发来新问题；
- 两者会拿到不同临时 `AgentSession` 和不同 `CancelToken`，可以同时执行。

## 6. EventBus 事件路由

`AgentSession` 内部通过 EventBus 发送事件，例如：

- `Done`
- `TodoListUpdated`
- `AskUserQuestion`
- `ToolComplete`
- `Error`

这些事件原本是给 CLI/TUI renderer 用的，不自带会话 ID。通讯平台并发后，如果只靠“当前 active conversation”全局变量，就可能出现 A 群事件被发到 B 群。

为了解决这个问题，平台层新增 `agent.platforms.context`：

```python
set_current_platform_conversation(conversation)
get_current_platform_conversation()
reset_current_platform_conversation(token)
```

QQ 适配器在调用 `state.session.chat_async()` 前绑定当前 `ConversationKey`，结束后恢复。`PlatformEventRenderer` 渲染事件时优先读取这个 `ContextVar`，再回退到串行 active conversation。

这让事件路由满足：

- 并发通讯会话：按 `ContextVar` 路由；
- 旧单线程测试和简单调用：按 `begin_run/end_run` 的 active conversation 路由；
- CLI/TUI：没有平台上下文，不进入通讯平台 renderer。

## 7. 工具状态隔离

大多数工具是无状态的，例如 `file_read`、`grep`、`glob`。但有些工具有运行时状态：

- `todo` 有内存任务列表；
- `ask_user_question` 需要等待用户回答；
- `send_message_asset` 需要把工具结果转成平台出站文件。

### 7.1 todo

`TodoTool` 是全局注册的工具实例。如果只隔离 `AgentSession`，但 `TodoTool.store` 仍然全局共享，就会出现 A 群的任务列表被 B 群读到。

因此 `TodoTool` 现在会读取 `get_current_platform_conversation()`：

- 没有平台上下文：使用默认 `self.store`，保持 CLI/TUI 行为；
- 有平台上下文：按 `ConversationKey.stable_id` 获取独立 `TodoStore`。

### 7.2 ask_user_question

`ask_user_question` 的等待和回填走 `QuestionRegistry`。通讯平台里用户回复 `1`、`1,3`、`其他: ...` 或 `取消` 时，`PlatformEventRenderer` 会优先尝试提交到 pending question，而不是启动新一轮 agent。

当前实现中，平台 session 会同步使用主 session 的 `question_registry`。原因是工具注册表和 `AskUserQuestionTool` 是进程级装配的，保持一份 registry 能让 TUI/QQ 复用同一套工具等待机制。真正的隔离键在 `PlatformEventRenderer` 的 pending question 映射里，它按 `ConversationKey` 保存“哪个会话正在等哪个问题”。

### 7.3 send_message_asset

`send_message_asset` 工具不直接发送 QQ 或微信消息，而是返回结构化 JSON。`PlatformEventRenderer` 根据当前 `ConversationKey` 把资源段交给对应平台适配器发送。这样文件发送能力也跟随事件路由，不会发错群。

## 8. 上下文与持久化边界

无论本地 session 还是通讯平台 session，长期上下文都只保存文本化摘要：

- 用户文本；
- final answer；
- `【工作记录】`；
- compact 摘要；
- 附件元数据和 OCR/ASR 摘要；
- 文件发送记录的路径、hash、大小等审计信息。

不会长期保存：

- OpenAI tool calling 的 `role=tool` 协议现场；
- `assistant.tool_calls`；
- 大段工具原始 stdout；
- 文件正文全文；
- 图片/音频二进制；
- base64 或 data URI。

这样做的原因是：跨轮恢复需要的是“下一轮继续任务需要知道什么”，不是复刻上一轮 API 请求的全部现场。

## 9. TUI 为什么不受通讯平台隔离影响

TUI 启动命令固定是：

```text
python run_agent.py --transport jsonrpc --memory-system light
```

QQ 模式启动命令是：

```text
python run_agent.py --transport qq
```

只有 QQ 分支会传入：

```python
communication_platform="qq"
session_factory=runner.get_or_create_platform_session
```

因此 TUI 不会：

- 注册 `send_message_asset`；
- 注入通讯平台系统提示；
- 使用 `.cbagent/platform_sessions/`；
- 按 `ConversationKey` 自动创建 platform session。

TUI 仍然使用普通 `.cbagent/sessions/`，并通过 `/sessions`、`/new`、`/switch` 管理本地多会话。

## 10. 未来接微信的复用方式

微信适配器需要新增的是协议翻译层：

```text
微信回调事件
  -> InboundMessage(conversation=ConversationKey("wechat", kind, id), ...)
  -> AgentSession.chat_async()
  -> EventBus events
  -> PlatformEventRenderer
  -> OutboundMessage
  -> 微信发送 API
```

可以直接复用的部分：

- `ConversationKey`；
- `InboundMessage` / `OutboundMessage`；
- `PlatformEventRenderer`；
- `AgentRunner.get_or_create_platform_session()`；
- `ContextVar` 事件路由；
- `TodoTool` 平台会话隔离；
- `send_message_asset` 工具结果协议；
- 同一会话 busy、不同会话并发的运行模型。

微信需要单独实现的部分：

- 鉴权和连接方式；
- 私聊/群聊消息解析；
- 群聊唤醒策略；
- 图片、语音、文件下载；
- 文本、图片、文件发送 API；
- 平台特有的消息 ID、引用消息、撤回等事件。

## 11. 测试策略

项目级会话隔离需要覆盖三类测试：

1. 本地 session 测试：
   - `create_session()` 后内存 history 清空；
   - `switch_session()` 只恢复目标 session；
   - 非法 session id 不能越权访问路径；
   - busy 时不能切换 session。

2. 通讯平台测试：
   - 不同 `ConversationKey` 创建不同 `AgentSession`；
   - 同一会话 busy 会被拒绝；
   - 不同会话可以并发；
   - `ContextVar` 能把 `Done` 等事件发回正确会话。

3. 工具状态测试：
   - `todo` 在不同 QQ 群/好友之间不串；
   - `ask_user_question` 的编号回复只消费对应会话的 pending question；
   - `send_message_asset` 资源段按当前会话发送。


## 12. 总结

cb-agent 的会话隔离可以概括成两层：

- 本地层：`.cbagent/sessions/` + `/sessions`、`/new`、`/switch`，解决 CLI/TUI 多任务切换；
- 平台层：`.cbagent/platform_sessions/<platform>/<conversation>/sessions/` + `ConversationKey`，解决 QQ/微信等通讯软件天然多会话并发。

两层最终都落到同一个核心原则：每个会话拥有独立 `AgentSession.history` 和独立 `LocalSessionStore`。前端、通讯平台和工具事件只是围绕这个核心做路由、降级和展示。
