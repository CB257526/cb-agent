# 多模态图像历史与缓存重构技术报告

## 1. 报告范围

本文记录 2026-07-31 已落地的多模态历史重构。覆盖：

- 用户图片附件；
- `load_image` 本地图片和远程图片；
- 工具循环、下一用户回合和进程重启；
- canonical history 与 `history.jsonl`；
- provider 请求序列化；
- 自动、手动和 mid-turn compact；
- Context token 估算与消息日志；
- 旧 data URI 会话的一次性迁移。

本文描述已经实现的 Chat Completions 主链路，不是计划文档。完整设计背景见
`docs/多模态图像历史与缓存重构计划.md`。

## 2. 重构前的问题

旧实现存在两类不一致：

1. 用户附件首次请求包含 data URI，但持久化或下一轮可能使用不同表示。
2. `load_image` 通过 `pending_images` 进程内缓冲传图，图片不是工具终态的一部分。

当旧图片消息从 data URI 变成 filepath、摘要、占位符或直接消失时，下一请求在该消息
之后的共同前缀全部失效。即使 assistant/tool/final answer 本身没有变化，provider 也无法
继续复用旧图片之后的 Prompt Cache。

进程内缓冲还存在恢复缺口：工具可能已经完成并产生副作用，但进程在缓冲 drain 或
bridge 追加前退出。重启只能恢复文本 tool result，无法证明模型曾经或应该看到哪张图。

## 3. 最终不变量

当前实现遵守以下约束：

1. canonical history 只保存 provider 无关的逻辑消息。
2. 图片正文按 SHA-256 保存到 `MediaBlobStore`，history 只保存不可变 `ImageRef`。
3. 普通用户回合和工具循环只追加 history，不改写旧图片消息。
4. data URI 只在 provider 请求边界临时生成，不能回写 history、journal 或日志。
5. 同一 `ImageRef` 每次展开为相同 MIME、base64 正文和 JSON 字段结构。
6. `load_image` 图片属于正式工具终态，必须绑定真实 `tool_call_id`。
7. compact 摘要请求只看图片清单；retained tail 和 active turn 保留原始 `ImageRef`。
8. 图片视觉成本进入窗口预算，不能因 base64 脱敏而被估成零。

## 4. 用户附件流程

用户发送图片后，主链路如下：

```text
读取并校验附件
-> MediaBlobStore.put_bytes()
-> 生成 ImageRef
-> history.append(user text + image_ref)
-> history.jsonl 写入逻辑消息
-> Message.to_provider_dict(media_store)
-> 临时展开为 image_url(data URI)
-> 发起 provider 请求
```

下一工具轮和下一用户回合仍从同一条逻辑 user 消息展开。源文件之后被覆盖、重命名或
删除，不影响旧 `ImageRef`，因为 provider 正文来自内容寻址 blob，不再读取原路径。

逻辑 history 示例：

```json
{
  "role": "user",
  "content": [
    {"type": "text", "text": "请查看图片"},
    {"type": "image_ref", "image_ref": {"blob_id": "sha256:...", "mime_type": "image/png"}}
  ]
}
```

provider 边界临时投影：

```json
{
  "role": "user",
  "content": [
    {"type": "text", "text": "请查看图片"},
    {"type": "image_url", "image_url": {"url": "data:image/png;base64,...", "detail": "auto"}}
  ]
}
```

`ConversationHistory.logical_messages()` 明确服务 journal 和本地诊断；
`provider_messages(media_store)` 才能展开图片。有 ImageRef 却未提供媒体存储时会直接
报错，禁止把项目内部 `image_ref` 内容块误发给 provider。

## 5. MediaBlobStore

媒体目录位于项目 `.cbagent/media`，所有本地会话共享同一内容库：

```text
.cbagent/media/blobs/sha256/<前两位>/<完整 SHA-256>
.cbagent/media/metadata/sha256/<前两位>/<完整 SHA-256>.json
```

已实现：

- SHA-256 内容寻址和同图去重；
- 20 MiB 默认硬上限；
- 图片 MIME 校验；
- 宽高和视觉 token 估算；
- UUID 临时文件加原子 replace，支持并发摄取；
- 读取时校验 SHA-256 与字节长度；
- 本地文件、远程 URL、旧 data URI 三种摄取入口；
- 固定 MIME 和无换行 base64 的确定性 data URI 展开。

`ImageRef` 保存 schema version、blob ID、SHA-256、MIME、字节数、尺寸、detail、文件名、
来源类型、规范化版本和视觉 token，不保存原始路径或图片正文。

## 6. load_image 工具流程

旧 `tools/tools/pending_images.py` 已删除。当前流程为：

```text
assistant.tool_calls(call_id)
-> load_image 固化图片并返回 ToolModelResult(text, image_ref)
-> ToolExecutor 生成 ToolCallResult(result, model_content)
-> result callback 写 tool checkpoint（含 model_content metadata）
-> 按 assistant 声明顺序追加全部 role=tool 终态
-> 生成一条正式 tool_image_bridge user 消息
-> 下一轮从全量 history 构造 provider 请求
```

结构化图片不直接塞进 `role=tool`，因为多数 Chat Completions provider 不接受这种内容。
`agent/tool_model_content.py` 在所有 tool 终态之后生成 bridge，并把真实 call ID 写入
metadata。并行工具也按 assistant 声明顺序合并，不依赖线程完成顺序。

`ToolModelResult` 当前只允许合法 `image_ref` 内容块。工具若尝试通过该接口返回 data URI
或未知内容类型，会在进入 checkpoint/history 前失败，不能绕过媒体落盘边界。

### 6.1 崩溃恢复

如果进程在 tool checkpoint 后、bridge append 前退出，`HistoryJournal.recover()` 会：

1. 按原 call ID 恢复 tool 终态；
2. 查找该回合尚未被 bridge 覆盖的 `model_content`；
3. 在全部 tool 消息之后补一条 bridge；
4. 追加 `turn_aborted`，明确禁止自动重放有副作用工具。

恢复逻辑按 `turn_id` 隔离，不能因未来复用同一个 call ID 而套用旧 bridge。再次重启时
不会重复补写。

## 7. Compact 图片语义

`agent/compaction_view.py` 是只供摘要请求使用的派生视图：

- `image_ref` 转为包含文件名、MIME、SHA-256、字节数、尺寸和 call ID 的文本清单；
- 旧 data URI 只保留 MIME 与长度；
- 旧远程 URL 去掉 query 和 fragment；
- 不读取 blob，不生成 base64，不让摘要 provider 重新拉取远程图片。

正式 compact 仍先按完整用户回合和工具协议拆成：

```text
summarized_prefix + retained_tail + active_turn
```

只有 `summarized_prefix` 进入 compaction view。`retained_tail` 与 mid-turn `active_turn`
保留逻辑 `ImageRef`，安装 replacement 后由普通 provider serializer 重新展开原图。因此
compact 不会把保留尾部图片永久降级为摘要或 filepath。

## 8. Token、日志与 UI

窗口估算现在分成两部分：

```text
JSON 文本 token（data URI 使用短占位符）
+ ImageRef / image_url 的视觉 token
```

用户附件、`load_image`、history 分区、compact post-budget 和当前完整请求使用同一视觉
估算规则。provider 返回实际 prompt usage 后，现有实际值覆盖机制保持不变。

`MessageLogger` 在内部强制调用递归脱敏。即使调用方误传原始 provider payload，日志也
不会写入 data URI；普通长文本、tool calls 和 tool results 仍保持完整。

TUI/RPC history 投影识别 `image_ref`，只显示文件名短标签。旧 `image_url` 统一显示
`[image]`，不会把 legacy base64 带进前端 payload。

## 9. 旧会话迁移

AgentSession 启动或切换会话时扫描恢复后的当前 history。发现旧 data URI 后：

```text
严格解码和校验
-> 写入 MediaBlobStore
-> 生成 ImageRef replacement history
-> journal 追加 reason=legacy_image_ref_migration 的新 generation
```

迁移只发生一次。旧 journal 事件作为审计事实保留，不原地重写；因此旧会话文件的历史
事件可能仍含 data URI，但当前 generation、后续 append 和新建会话不会再写 raw base64。
已经被旧实现降级成纯文本摘要且没有原始正文的图片不会被伪造恢复。

## 10. 缓存连续性

普通运行中的连续请求满足：

```text
上一请求 messages
== 下一请求 messages 的结构化前缀
```

图片处的 provider 表示由同一 `ImageRef` 确定性展开，因此旧图片之后的 assistant、tool、
bridge 和 final answer 不会因下一用户回合而失去前缀缓存。明确允许重建前缀的边界只有
正式 compact、旧会话迁移、clear 和模型/provider 配置变化。

Chat Completions 仍会在网络请求中重复携带 base64。这是传输协议限制，不代表 provider
必须重复 prefill。减少网络上传需要未来的 Responses cursor 或 provider 文件 ID。

## 13. 保留边界

本次没有实现以下未来能力：

- Responses API 的 `previous_response_id` / provider 文件 ID；
- Anthropic 原生 image/tool_result adapter；
- 自动 blob mark-and-sweep。

当前仓库的模型调用主链路是 Chat Completions，因此本次先完整闭合该协议。自动 GC 暂不
启用，是为了避免在 journal 旧 generation、崩溃 checkpoint 和会话切换之间误删仍可恢复
的 blob；在有引用扫描和保留期策略之前，宁可增加磁盘占用，也不能静默破坏历史。
