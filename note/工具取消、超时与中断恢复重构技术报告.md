# cb-agent 工具取消、超时与中断恢复重构技术报告

## 1. 报告范围

本文记录 2026-07-28 完成的工具取消、超时和中断恢复重构。对应实现提交为
`7663936 refactor: 重构工具取消与中断恢复`。

本报告不重复《用户中断工具执行机制对比技术报告》中对 Codex 和 Claude Code 的
源码分析，而是回答 cb-agent 工程落地中的五个问题：

1. 为什么原来的工具超时和用户取消没有真正生效；
2. 为什么只增加取消令牌检查仍然不能解决问题；
3. Bash、MCP、普通 Python 工具分别应该怎样停止；
4. 中断时如何保证 assistant/tool 消息和历史记录完整；
5. 本次改造已经保证什么，仍然有哪些明确边界。

## 2. 故障现象与影响

最初的直接症状是一个 CodeGraph MCP 工具持续运行至少五分钟，配置的超时没有让
调用被强制结束。此时会话表现为一直 busy，后续循环无法推进，用户虽然可以提交取消
请求，但取消只改变了内存中的布尔状态，正在运行的工具仍然占据执行线程。

这个问题不只影响某一个 MCP 工具。重构前的执行路径存在以下共同风险：

- 同步 `Tool.run()` 一旦进入阻塞调用，通用执行器没有可用的抢占点；
- 临时线程池退出时会等待已提交任务，外层取消 future 也不能杀死正在运行的线程；
- MCP 持久调用在无界 `future.result()` 上等待，既没有 deadline，也没有轮询取消；
- Bash 的取消令牌没有连接到底层子进程和进程组，Python 调用返回前命令会继续运行；
- tool loop 只在循环边界或下一次工具开始前检查取消，无法影响当前工具；
- 中断路径可能丢弃尚未形成完整结果的工具调用，留下孤立的
  `assistant.tool_calls`，也无法表达远端副作用是否已经发生。

因此，故障的本质不是“取消检查频率太低”，而是取消信号没有贯穿到实际运行时，
执行协议也没有定义被中断工具的终态。

## 3. 根因分析

### 3.1 布尔取消令牌表达能力不足

旧 `CancelToken` 只包装 `threading.Event`。它可以回答“是否取消”，但不能回答：

- 是用户取消、工具超时还是会话关闭；
- 单个工具的截止时间还剩多久；
- 哪个 Bash 进程组或 MCP future 需要立即清理；
- 父 turn 取消后，子工具应该记录什么原因；
- 多个取消来源竞争时，哪个原因应成为最终事实。

缺少这些信息后，执行器只能在调用前后检查标记，无法做运行时 teardown。

### 3.2 Python 线程不能安全硬杀

`ThreadPoolExecutor` 的 `Future.cancel()` 只能取消尚未开始的任务。任务已经在线程中执行
后，Python 没有安全、通用的线程终止机制。强行让上层放弃等待，会留下一个仍可能
读写文件、发网络请求或修改外部系统的后台线程。

因此，执行器不能把“future 已取消”误认为“工具已经停止”。正确做法必须按工具的
运行时能力分类：

- 外部进程或异步请求：主动终止底层运行时；
- 能检查上下文的 Python 工具：协作取消；
- 旧的同步阻塞工具：阻止后续 loop，但等待当前工具真实返回。

### 3.3 MCP 存在无界等待

重构前持久 MCP 客户端通过无超时的 `future.result()` 等待事件循环中的 coroutine。
只要 server 不返回，调用线程就永久阻塞。即使 turn 已经取消，取消令牌也没有传给
该 future，更不会让连接失效。

这正是 CodeGraph 长时间不结束的直接技术原因。

### 3.4 Bash 只停止等待不能停止命令

对 Bash 而言，停止 Python 层等待并不等于停止命令。命令可能继续运行，并继续派生
子进程。只终止 shell 本身也不充分，因为孙进程可能仍然存活。

所以 Bash 取消必须以独立进程组为边界，对整个进程组执行 TERM、短暂等待、KILL
升级和最终回收。

### 3.5 历史没有中断终态协议

模型已经输出 `assistant.tool_calls` 后，这些调用就成为协议历史的一部分。如果中断时
直接抛弃正在运行或尚未开始的结果，会产生两个问题：

1. 下一次模型请求看到孤立 tool call，违反 tool calling 配对要求；
2. 系统无法区分“没有执行”“确认停止”和“可能已经产生副作用”。

这要求执行状态、持久化状态和模型可见消息使用同一套终态语义。

## 4. 重构目标与边界

本次重构的目标是：

- 显式用户取消能够主动打断 LLM、Bash 和 MCP；
- 每个工具调用都有且只有一个终态；
- 默认工具超时为 120 秒，并支持分层覆盖；
- 中断不会留下孤立 tool call；
- Gateway 只有在运行时清理和历史提交完成后才宣告最终取消；
- 新执行链替代旧主路径，只保留必要的兼容入口。

本次明确不做：

- 新消息不会隐式取消正在运行的 turn，仍使用 busy/排队语义；
- 不尝试硬杀任意 Python 线程；
- 不把远端 MCP 请求的本地取消解释为远端事务回滚；
- 不引入任意 Python 工具的独立工作进程隔离。

## 5. 总体设计

新的执行和持久化路径可以概括为：

```text
turn CancellationContext
        |
        +-- LLM 流取消
        |
        +-- child CancellationContext + deadline
                |
                +-- ToolExecutionContext
                        |
                        +-- Bash 进程组控制器
                        +-- MCP future/连接控制器
                        +-- Python 工具协作检查

assistant_tool_calls -> tool_started -> tool_terminal
                                      -> turn_aborted
                                      -> transcript/history commit
                                      -> final Cancelled
```

核心原则是：**取消从 turn 向运行时传播，工具结果从运行时向历史收敛**。运行时可以
使用不同手段停止，但最终必须映射到统一状态，并按原始 tool call 顺序进入消息。

## 6. 取消上下文

`agent/cancel.py` 将原布尔令牌扩展为 `CancellationContext`，主要能力包括：

- 记录 `reason` 和 `cancelled_at`；
- 使用单调时钟 deadline；
- 通过 `child(deadline=...)` 建立 turn 与单工具的父子关系；
- 父级取消向所有子工具传播真实原因；
- `throw_if_cancelled()` 提供协作取消边界；
- `add_cancel_callback()` 允许运行时注册即时清理动作；
- 第一次取消原因生效，后续竞争取消保持幂等。

取消原因统一为：

| 原因 | 语义 |
| --- | --- |
| `user_cancelled` | 用户明确取消当前 turn |
| `tool_timeout` | 单工具超过解析后的 deadline |
| `session_shutdown` | 会话关闭触发清理 |
| `parent_cancelled` | 无法取得父级具体原因时的传播兜底 |

旧名称 `CancelToken` 仍是兼容别名，因此原有 LLM 和工具调用方无需同时全部迁移。

## 7. 工具执行上下文与状态机

新增的 `ToolExecutionContext` 为单次调用携带：

- `turn_id`；
- `round_idx`；
- `call_id`；
- `tool_name`；
- deadline；
- 子级 `CancellationContext`。

工具能力分为三类：

| 模式 | 行为 | 当前适用对象 |
| --- | --- | --- |
| `runtime` | 注册运行时控制器，取消时主动 teardown | Bash、MCP |
| `cooperative` | 工具在循环和阻塞边界检查上下文 | 已迁移的 Python 工具 |
| `blocking` | 无法安全抢占，只能等待真实返回 | 旧同步工具默认值 |

每个 `call_id` 只允许经历一次：

```text
planned -> started -> terminal
```

终态统一为：

| 状态 | 含义 |
| --- | --- |
| `completed` | 工具正常完成 |
| `failed` | 工具执行失败 |
| `cancelled_before_start` | 已规划但未执行任何工具代码 |
| `cancelled` | 已开始，且已确认按取消路径停止 |
| `timed_out` | 已开始，因 deadline 到期而停止 |
| `unknown` | 已开始，但无法确认执行或副作用状态 |

副作用确定性单独记录为 `none`、`completed`、`may_have_occurred` 或 `unknown`。
这避免把“本地已经停止等待”错误表述成“远端没有执行”。

### 7.1 串行执行

当前工具收到取消后，执行器立即通知其运行时。后续尚未启动的调用不再执行工具
代码，直接生成 `cancelled_before_start` 结果。

### 7.2 并行执行

取消发生时，执行器会：

1. 取消线程池中尚未开始的 future；
2. 通知所有已运行工具的取消上下文；
3. 收集每个调用的唯一终态；
4. 按模型原始 `tool_calls` 顺序返回，而不是按完成顺序返回。

执行器不再依赖退出时强制等待全部任务的临时线程池上下文。对于无法抢占的
`blocking` 工具，系统会显示取消正在处理并等待真实返回，不会将后台线程从 turn 中
静默分离。运行超过 100ms 的阻塞工具会记录告警，作为后续迁移依据。

## 8. 超时策略

`ToolTimeoutPolicy` 提供统一超时解析，全局默认值为 120 秒，可通过
`CB_AGENT_TOOL_TIMEOUT_SEC` 覆盖。优先级为：

1. 单次调用显式超时，例如 Bash 的 `timeout`；
2. MCP server 的 `tool_timeout_sec`；
3. 工具实例的 `default_timeout_seconds`；
4. 全局默认值。

字段缺失才继续读取下一层；`0` 或 `null` 表示该层显式禁用。负数、布尔值、NaN
和 Infinity 会被拒绝，防止配置被 Python 的隐式类型规则误接受。Bash 对外仍保持
毫秒单位兼容，执行器内部统一换算为单调时钟 deadline。

用户取消与工具超时共用清理机制，但最终分别记录为 `cancelled` 和 `timed_out`，
便于 UI、日志、恢复和模型决策准确区分。

## 9. Bash 主动终止

`tools/tools/bash_tool.py` 的新路径在进程启动后立即注册进程组取消控制器。取消或
超时时按以下顺序处理：

1. 命令在独立进程组中启动；
2. 向整个进程组发送 TERM；
3. 等待 50ms，让支持优雅退出的进程清理；
4. 对残留进程组发送 KILL；
5. 回收子进程以及 stdout/stderr 管道；
6. 将已经产生的输出作为 `partial_output` 保留。

终止整个进程组是必要条件，否则 shell 派生的子进程可能在 turn 结束后继续运行。
测试覆盖了长时间 `sleep`、取消竞争和部分输出保留，其中真实 `sleep 30` 在取消后
一秒内退出。

## 10. MCP 取消、超时与连接失效

MCP 是本次故障的重点修复对象。改造后的关键行为是：

- 删除持久调用中的无界 `future.result()`；
- 以 50ms 边界竞争完成、取消和 deadline；
- 用户取消时调用 `future.cancel()`，让 `CancelledError` 进入 MCP coroutine；
- 连接建立、同 server 锁等待和实际工具调用都可以观察取消；
- 同一 MCP server 调用串行化，避免取消一个请求破坏同连接上的其他请求；
- 在 in-flight 取消或超时后使连接失效，下次调用自动重连；
- 完整保留和校验 `mcp.json` 中的 `tool_timeout_sec`。

对于本地 stdio MCP，连接清理会关闭 transport，并在需要时结束 server 进程。对于
HTTP/SSE MCP，本地可以关闭请求和连接，但不能证明远端业务已经回滚，因此副作用
通常标记为 `may_have_occurred`，需要下一轮在重试前检查外部状态。

永久挂起的内存 MCP 测试在 50ms deadline 下约 58ms 返回，证明超时不再受 server
是否主动响应约束。HTTP、SSE、stdio 和内存传输均有针对性覆盖。

## 11. active-turn 日志与历史事务

tool loop 运行期间继续在本轮 `messages` 中追加完整协议消息，但不逐条修改正式
`self.history`。运行中状态写入 `active_turn.jsonl`，收尾完成后再把整个 turn 一次性
提交到 transcript 和 history。

新 journal 事件为：

```text
turn_started
assistant_tool_calls
tool_started
tool_terminal
assistant_final
turn_aborted
```

工具真正开始前先写入并 flush `tool_started`。运行时清理完成后写入唯一的
`tool_terminal`。中断归档前写入 `turn_aborted`。旧 `tool_completed` 只保留读取兼容，
新主路径不再写入，从而避免长期保留两套写协议。

### 11.1 手动中断的持久化规则

| 工具阶段 | 持久化结果 |
| --- | --- |
| 已正常完成 | 保留原始 `completed` 结果 |
| 正在执行且确认停止 | 写入 `cancelled` 工具消息 |
| 尚未开始 | 写入 `cancelled_before_start` 工具消息 |
| 已开始但无法确认停止或副作用 | 写入 `unknown` 工具消息 |

任何已经保留的 `assistant.tool_calls` 都必须有相同 `tool_call_id` 的终态 tool 消息。
取消结果使用稳定 JSON 结构，至少包含状态、工具名、call ID、原因、副作用状态和
部分输出，使下一轮模型能够判断是否重试或先检查外部状态。

### 11.2 崩溃恢复

恢复 active turn 时：

- 有 `tool_started`、无终态：合成 `unknown`；
- 已规划、无 `tool_started`：合成 `cancelled_before_start`；
- 有终态：恢复原始终态；
- 为所有保留调用补齐模型可见的 tool result；
- 末尾追加模型可见但普通 UI 隐藏的 `<turn_aborted>` 消息。

这样既满足模型协议，又不会掩盖工具可能已经产生的副作用。

## 12. Gateway 取消时序

`session.cancel` 的 RPC 响应只表示“取消请求已接受”，不再表示工具已经停止。ACK
使用 `accepted`、`completed` 和 `closed_streams` 描述即时状态。

最终事件顺序固定为：

```text
请求运行时清理
-> 补齐全部工具终态
-> 写 turn_aborted
-> 提交 transcript/history
-> 清理 active turn
-> emit Cancelled
-> 释放 busy
```

因此，客户端快速收到 ACK 后仍可展示“取消处理中”。只有最终 `Cancelled` 事件到达，
才代表运行时清理和历史归档已经结束。测试同时验证了最终事件只发送一次，busy 不会
在持久化前提前释放。

## 13. 兼容策略与代码收敛

本次重构优先替换旧主路径，没有在仓库中并行保留一套新的旁路实现：

- `Tool.run_with_context(parameters, context)` 成为生产执行入口；
- 旧 `Tool.run(parameters)` 仅用于已有工具和直接调用兼容；
- `CancelToken` 仅作为 `CancellationContext` 的名称兼容；
- 旧 `tool_completed` 只读，不再写；
- 正常完成的 OpenAI tool calling 消息结构保持不变；
- 新状态字段只出现在失败、取消、超时和恢复合成结果中。

主要改动文件包括：

| 模块 | 责任 |
| --- | --- |
| `agent/cancel.py` | turn 级取消上下文和运行时回调 |
| `agent/tool_execution.py` | 工具上下文、终态、副作用和超时策略 |
| `agent/executor.py` | 串并行调用状态机和有序结果收集 |
| `agent/session.py` | tool loop 取消收尾和 history 提交 |
| `agent/work_context.py` | active-turn journal 与崩溃恢复 |
| `agent/transport/gateway.py` | 快速取消 ACK 与最终事件时序 |
| `tools/tools/bash_tool.py` | 进程组终止和部分输出 |
| `tools/mcp_tools/mcptool.py` | MCP deadline、取消、串行化和重连 |
| `tools/tool.py`、`tools/toolRegistry.py` | 新执行入口与兼容适配 |

## 15. 已解决问题与行为变化

重构后，最初的问题得到以下直接修复：

- MCP 不再能够因为无界 `future.result()` 永久占用工具线程；
- 默认 120 秒 deadline 会真实进入执行路径；
- 用户取消会连接到 Bash 进程组和 MCP coroutine，而不是只设置标记；
- queued 工具不会在 turn 已取消后继续启动；
- 并行结果顺序保持模型原始调用顺序；
- 中断结果不再被静默丢弃；
- history 中每个 tool call 都有配对终态；
- 客户端能区分“取消请求已接受”和“回合已经完成清理”。

## 16. 剩余限制与后续建议

### 16.1 阻塞型 Python 工具

当前无法安全硬停不检查上下文的进程内 Python 工具。系统会停止后续 tool loop，
但仍等待当前工具返回。若业务要求任意 Python 工具都可强制停止，应引入独立工作
进程，并设计进程终止、IPC、结果落盘和副作用声明，不能使用线程异步注入异常。

### 16.2 远端副作用

MCP HTTP/SSE 连接断开只证明客户端停止等待。对远端写操作，下一轮应根据
`effect_state=may_have_occurred` 先查询外部状态，再决定是否重试，避免重复写入。

### 16.3 迁移优先级

建议持续记录 `blocking` 工具超过 100ms 的告警，并优先把高频、长耗时和有副作用
的工具迁移到 `runtime` 或 `cooperative` 模式。迁移时必须同时补充取消、超时、
完成竞争和历史终态测试。

### 16.4 可观测性

后续可增加按工具统计的取消延迟、强杀次数、连接失效次数、`unknown` 终态数量和
副作用不确定率。`unknown` 持续升高通常说明运行时缺少可确认的终止协议。

## 17. 维护约定

以后修改本机制时，应同时维护以下不变量：

1. 取消必须抵达真实运行时，不能只在循环边界检查布尔值；
2. 每个已保留 tool call 必须有且只有一个终态 tool result；
3. 远端停止等待不能冒充副作用已经回滚；
4. transcript/history 提交必须先于最终 `Cancelled`；
5. 新协议替代旧协议后，旧代码只保留必要兼容，不保留双写主路径；
6. 重大功能重构必须在 `note/` 中同步产出技术报告，记录问题、根因、设计、改动、
   验证证据、兼容策略、限制和后续工作。
