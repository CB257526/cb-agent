# cb-agent 跨轮工作上下文技术报告

> 本报告对应本次“工具轨迹压缩 + 本地会话恢复”改造。
> 关键源代码：[agent/work_context.py](../agent/work_context.py)、[agent/session.py](../agent/session.py)、[run_agent.py](../run_agent.py)。

---

## 0. 背景：为什么原来的 history 不够

原来的 `AgentSession` 在一轮 chat 结束后，只把两类消息放入 `self.history`：

- 用户输入：`Message.create_user_message(user_query)`
- 最终回答：`Message.create_assistant_message(final_answer)`

这对普通聊天够用，但对代码 agent 不够。代码 agent 的很多“理解”发生在工具循环中：

- `file_read` 看过哪些文件、哪几段代码
- `bash` 跑过哪些命令、当前 cwd 和退出码
- `file_write` 改过哪些文件、增删了多少行
- 工具报错、后台任务输出、RAG/搜索结果等

这些信息在本轮内会进入 OpenAI 风格的 `messages`，所以模型可以继续 tool calling；但本轮结束后，工具消息不会进入 `history`。下一轮模型只看到用户问题和最终回答，容易丢失“刚才已经看过什么/确认过什么”的工作现场。

---

## 1. 核心设计：四条上下文线分工

这次改造没有把所有工具结果粗暴塞进 `history`，而是拆成四条线：

| 数据线 | 生命周期 | 内容 | 用途 |
|---|---|---|---|
| `messages` | 单轮 tool loop 内 | 完整 system/user/assistant/tool 协议消息 | 本轮继续调用工具和推理 |
| `TraceCollector` | 单轮 chat 内 | 被限制后的工具事实摘要 | 生成跨轮工作记录 |
| `self.history` | 进程内多轮 | user、final answer、`【工作记录】` assistant 消息 | 下一轮 `[Context]` |
| `.cbagent/sessions` | 跨进程 | transcript + state | 重启恢复和高优先级 `[State]` |

最重要的边界是：**不跨轮保存 OpenAI 协议里的 `role=tool` 消息**。

原因是 `role=tool` 必须对应同一轮上文里的 assistant `tool_calls` 和 `tool_call_id`。跨轮恢复时，如果把旧的 `tool` 消息直接塞回新一轮上下文，很容易出现协议不合法或语义错位。工作记录因此被包装成普通 assistant 文本：

```text
【工作记录】
用户任务：读 a.txt
读取文件：a.txt (head-100, returned=100) ...
执行命令：pytest ... (exit=0, cwd=...)
```

## 2. 工具轨迹压缩策略

新增模块 `agent/work_context.py` 负责工具轨迹压缩。核心结构是：

- `TraceEntry`：一次工具调用的安全摘要
- `TraceCollector`：一次 chat 内的 trace 列表
- `WorkRecord`：一轮结束后的工作记录和结构化状态
- `RuleTraceSummarizer`：规则压缩兜底
- `TraceSummarizer`：超过阈值时的静默 LLM 压缩

### 2.1 单工具结果限制

每个工具结果最多保留 100 字符摘要。这个限制只作用于跨轮 trace，不影响本轮 `messages`。

也就是说：

- 本轮模型仍能看到完整工具返回，保证 tool loop 推理能力。
- 下一轮只看到压缩后的工作事实，避免上下文爆炸。

### 2.2 工具类型白名单

不同工具提取不同字段：

| 工具 | 保存内容 | 明确不保存 |
|---|---|---|
| `file_read` | path、mode、total_lines、returned_lines、truncated、短 content 预览 | 完整文件正文 |
| `file_write` | path、ok、type、bytes_written、lines_added、lines_removed、message | 写入的完整 content 参数 |
| `bash` | command、cwd、exit_code、output_file、短 stdout/stderr 预览 | 完整 stdout/stderr |
| `bash_task` | task_id、status、cwd、exit_code、output_file、短输出预览 | 完整后台输出 |
| 其他工具 | name、参数短摘要、错误状态、短结果摘要 | content/stdout/stderr/result 等大字段 |

这个策略让 transcript 可审计，但不会变成另一个“工具输出仓库”。

## 3. 每轮结束后的写入流程

在 `AgentSession._tool_loop()` 中，现在同时维护两份数据：

1. `messages`
   完整协议上下文。每个工具结果仍然以 `role="tool"` 追加，用于下一轮 `llm.think()`。

2. `trace_collector`
   压缩工具轨迹。每个 `ToolCallResult` 额外转成一条 `TraceEntry`。

一轮结束后，`AgentSession._chat_impl()` 的顺序是：

1. 追加用户消息到 `self.history`
2. 追加最终回答到 `self.history`
3. 如果本轮有工具调用，把 `trace_collector` 生成 `WorkRecord`
4. 将 `WorkRecord.text` 作为普通 assistant 消息追加到 `self.history`
5. 将本轮记录写入 `.cbagent/sessions/<session_id>/transcript.jsonl`
6. 将结构化工作态合并到 `state.json`

history 顺序因此变成：

```text
[user] 用户输入
[assistant] 最终回答
[assistant] 【工作记录】...
```

纯聊天轮次没有工具调用时，不生成 `【工作记录】`，避免无意义撑大 history。

## 4. 静默 LLM 总结

如果一轮 trace 字符串化后超过：

- 1000 字符，或
- 约 800 tokens

则优先调用 `TraceSummarizer` 做静默总结。它有一个非常重要的实现约束：

> 不调用 `llm.think()`，而是直接调用 `llm.client.chat.completions.create(..., stream=False)`。

原因是 `llm.think()` 是主回答流式路径，会向 `EventBus` 派发 `TextDelta` / `ReasoningDelta`。如果 summarizer 走这条路，前端会把“内部工作记录总结”误显示成助手回答。

静默总结只替换 `WorkRecord.text`，结构化字段仍来自规则提取：

- `files_seen`
- `files_modified`
- `recent_commands`
- `pending`
- `decisions`

这样即使 LLM 总结表述不稳定，也不会污染 `state.json` 的结构化事实。

如果静默总结失败，系统回退到 `RuleTraceSummarizer`，不会影响主对话完成。

## 5. 本地文件结构

本地持久化目录：

```text
.cbagent/
  sessions/
    index.json
    session_YYYYMMDD_HHMMSS_xxxxxxxx/
      transcript.jsonl
      state.json
```

### 5.1 index.json

只保存最近自动恢复的 active session：

```json
{
  "active_session_id": "session_20260602_120000_ab12cd34"
}
```

启动时 `LocalSessionStore` 读取它，并自动恢复对应 session。

### 5.2 transcript.jsonl

每轮一行 JSON：

```json
{
  "ts": "...",
  "user_query": "...",
  "final_answer": "...",
  "work_record": "【工作记录】...",
  "trace_entries": [...]
}
```

transcript 用于恢复最近 history 和人工审计。它只保存压缩 trace，不保存完整文件正文或完整命令输出。

### 5.3 state.json

state 是给模型下一轮快速使用的滚动工作态：

```json
{
  "turn_count": 3,
  "rolling_summary": "【工作记录】...",
  "active_task": "...",
  "files_seen": {},
  "files_modified": {},
  "recent_commands": [],
  "decisions": [],
  "pending": []
}
```

`state.json` 会被渲染成 `ContextPacket(priority=P1_STATE)`，进入 ContextBuilder 的 `[State]` 节。它比普通 history 更高优先级，适合保存“任务当前状态”。

## 6. 上下文注入路径

### 6.1 ContextBuilder 开启

`AgentSession` 会调用：

```python
builder.to_messages(
    user_query=user_query,
    conversation_history=self.history,
    system_instructions=system_instructions,
    additional_packets=[state_packet],
)
```

其中：

- `self.history` 进入 `[Context]`
- `state_packet` 进入 `[State]`

这让短期对话和长期工作态分层。

### 6.2 ContextBuilder 关闭

如果用户 `/ctx off`，系统仍会把本地 state 手工拼进 system prompt：

```text
[State]
关键进展与未决问题：
...
```

这样即使关闭 GSSC 流水线，也不会完全丢失跨轮工作状态。

## 7. /clear 的新语义

原来的 `/clear` 只清空内存 `history`。现在有本地自动恢复后，如果仍只清内存，重启就会从 `index.json` 恢复旧上下文，违背用户直觉。

因此 `/clear` 改为彻底清理：

1. `self.history.clear()`
2. 删除 active session 目录
3. 删除 `index.json`
4. 清空 `LocalSessionStore.active_session_id/state`

如果用户不重启、直接继续聊天，`LocalSessionStore.ensure_active()` 会在下一次写入时自动创建新 session。

## 9. 已知取舍与后续方向

### 9.1 当前只自动恢复最近 session

现在没有 session 列表和手动 resume 命令。`index.json` 只指向 active session，满足“启动自动恢复最近会话”的需求。

后续可以加：

- `/sessions`
- `/resume <session_id>`
- `/archive-session`

### 9.2 state 的滚动摘要是追加截断

当前 `rolling_summary` 使用追加后截断，不做复杂语义合并。这样实现简单稳定，但很旧的信息可能被挤掉。

后续可以在 state 过大时触发独立的 state compaction。

### 9.3 静默总结只替换文本，不改结构化事实

这是为了降低幻觉风险。后续如果要让 LLM 输出 JSON 结构化摘要，需要增加 schema 校验和字段白名单。

### 9.4 transcript 不是安全加密存储

`.cbagent/sessions` 是项目级本地文件，便于审计和恢复，但不加密。虽然完整工具输出不会保存，用户仍应避免在 prompt 或工具结果摘要中暴露高敏信息。

---

## 10. 一句话总结

这次改造把 cb-agent 从“只记住用户问题和最终回答”的聊天历史，升级为“能记住工作现场”的代码 agent 会话系统：本轮推理保留完整工具上下文，跨轮和重启恢复只保留严格压缩后的工作事实。
