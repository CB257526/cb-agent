# Codex、Claude Code 与 cb-agent 的用户中断工具执行机制对比

## 1. 报告目的

本文回答一个具体问题：当 Agent 正在执行工具时收到用户中断，系统应该等待工具自然结束，还是立即中断工具执行？如果立即中断，底层进程、MCP 请求、并行工具和会话历史分别如何处理？

分析对象为工作区中的三份代码：

- `外部代码/codex-main`：Codex Rust 实现。
- `外部代码/claude-code-main`：该目录自身声明为 Claude Code 的逆向/反编译重建版本。本文只能说明这个本地版本呈现出的设计，不能把所有细节视为 Anthropic 官方源码的确定行为。
- `cb-agent`：当前项目实现。

初始分析日期为 2026-07-27；2026-07-28 已在
`refactor/codex-tool-cancellation` 分支按本文结论完成首期重构。前文保留改造前
状态，末章记录实际落地结果。

## 2. 结论摘要

Codex 和本地 Claude Code 重建版都没有采用“设置取消标记，然后无期限等待当前工具自然结束”的单一策略。

Codex 的策略更接近强抢占：

1. 用户中断会立即取消整个 turn 的 `CancellationToken`。
2. 普通异步工具任务直接 `abort`。
3. Shell 等需要资源清理的工具先等待运行时完成进程 teardown，再结束工具任务。
4. turn 最多等待 100ms 的优雅退出，之后强制 abort 顶层 task。
5. 对被中断的工具生成与原 `call_id` 配对的 `aborted by user` 工具输出。
6. 在历史中持久化 `<turn_aborted>` 标记，并明确告知模型工具可能已经部分执行。

本地 Claude Code 重建版区分两种用户动作：

1. 用户明确按 Esc/Ctrl-C 取消当前回合：立即触发全局 `AbortController`。Bash 收到 signal 后杀进程树，MCP 调用收到同一个 signal；工具调用最终产生错误 `tool_result`，然后回合结束。
2. 用户在工具运行中直接提交下一条消息：只有当前运行工具全部声明 `interruptBehavior() === "cancel"` 时才抢占；默认行为是 `block`，新消息排队等待。当前代码中明确声明可取消的示例是 `SleepTool`，Bash 和 MCP 没有该声明，因此这一交互通常不会抢占它们。

cb-agent 当前则是协作式、边界式取消：

1. LLM 流能在 chunk 边界停止。
2. 串行工具只在每个工具开始前检查取消令牌。
3. 当前正在运行的工具不会被通用执行器中断。
4. 并行模式会等待全部已提交 future 自然完成。
5. MCP 持久调用在无 timeout 的 `future.result()` 上无限等待。

因此，cb-agent 当前行为既不同于 Codex 的强抢占，也没有 Claude Code 的工具级 `cancel/block` 能力声明。CodeGraph 卡死就是这个缺口的直接表现。

## 3. 三种“中断”必须分开讨论

设计中至少存在三种不同语义：

| 类型 | 用户意图 | 推荐行为 |
| --- | --- | --- |
| 明确取消当前回合 | “现在立刻停下” | 传播取消，终止可控工具，生成中断结果，结束 turn |
| 运行中提交下一条消息 | “先处理我刚发的新要求” | 按工具能力决定抢占或排队 |
| 工具超时 | “超过系统允许的最长执行时间” | 终止工具或停止等待，生成 timeout/unknown 结果 |

如果把三者都实现成同一个布尔 `cancelled`，会产生两个问题：

- 对不可安全抢占的写操作过度激进，可能留下不确定副作用。
- 对本应立即终止的 Bash、MCP 和网络读取过度保守，导致会话永久卡住。

Codex 主要解决第一种和第三种；Claude Code 的 `interruptBehavior` 额外解决了第二种。

## 4. Codex：取消当前 turn，并按运行时能力完成 teardown

### 4.1 用户中断入口

Codex 的中断入口最终调用：

```rust
sess.abort_all_tasks(TurnAbortReason::Interrupted).await;
```

位置：`外部代码/codex-main/codex-rs/core/src/session/handlers.rs:599-604`。

`abort_all_tasks()` 从 session 中取出 active turn，调用 `handle_task_abort()`，然后发出完整的 turn abort 生命周期事件：

- `外部代码/codex-main/codex-rs/core/src/tasks/mod.rs:492-520`
- `外部代码/codex-main/codex-rs/core/src/tasks/mod.rs:830-907`

### 4.2 顶层任务不是无限等待

`handle_task_abort()` 的处理顺序是：

1. 调用 `task.cancellation_token.cancel()`。
2. 最多等待 100ms，让任务观察取消并自行清理。
3. 超过 100ms 后执行 `task.handle.abort()`，强制取消 Tokio task。
4. 调用任务的 `abort()` 钩子进行额外清理。

相关常量和代码：

- `GRACEFULL_INTERRUPTION_TIMEOUT_MS = 100`：`codex-rs/core/src/tasks/mod.rs:67`
- 取消和等待：`codex-rs/core/src/tasks/mod.rs:830-850`
- 任务清理钩子：`codex-rs/core/src/tasks/mod.rs:852-858`

所以 Codex 不会为了等待业务工具“正常返回”而无限阻塞。它只提供一个很短的优雅退出窗口。

### 4.3 工具调度层直接竞争“结果完成”和“用户取消”

Codex 的单工具执行不是同步调用后再检查 token，而是：

```rust
tokio::select! {
    res = &mut dispatch_handle => { ... }
    _ = cancellation_token.cancelled() => { ... }
}
```

位置：`codex-rs/core/src/tools/parallel.rs:158-199`。

取消分支分成两类：

#### 普通异步工具

普通工具执行：

```rust
dispatch_handle.abort();
```

随后等待 JoinHandle 进入 cancelled 状态，并生成 aborted response。也就是说，上层不再等待工具业务自然结束。

#### 需要运行时清理的工具

部分工具通过 `waits_for_runtime_cancellation()` 声明：取消时不能只丢弃 future，必须等底层运行时完成资源清理。

Shell handler 返回 `true`：

```rust
fn waits_for_runtime_cancellation(&self) -> bool {
    true
}
```

位置：`codex-rs/core/src/tools/handlers/shell/shell_command.rs:240-247`。

此时工具调度器不会先 abort handler，而是等待 handler 观察 cancellation token、终止进程并返回。这里等待的是“取消清理完成”，不是“命令自然完成”。

### 4.4 Shell 会终止进程组

Codex 把 cancellation token 传入 shell runtime：

```rust
pub struct ShellRequest {
    ...
    pub cancellation_token: CancellationToken,
}
```

位置：`codex-rs/core/src/tools/runtimes/shell.rs:53-70`。

执行层在 `tokio::select!` 中同时等待子进程退出和 timeout/cancel。取消后：

1. 向整个进程组发送终止信号。
2. 给 TERM-aware 进程 50ms 清理窗口。
3. 仍未退出则杀死整个进程组。

位置：

- 取消竞争：`codex-rs/core/src/exec.rs:996-1020`
- 终止与升级：`codex-rs/core/src/exec.rs:1020-1045`
- `CANCELLATION_TERMINATION_GRACE_PERIOD = 50ms`：`codex-rs/core/src/exec.rs:66`

这说明 Codex 对 Shell 的真实语义是“立即发起终止并等待 teardown”，不是“等待 shell 命令自行结束”。

### 4.5 MCP 同时有调用超时和上层任务取消

Codex MCP connection manager 为每个 server 保存 `tool_timeout`，调用时传给底层 MCP 客户端：

```rust
client
    .call_tool(tool.to_string(), arguments, meta, client.tool_timeout)
    .await
```

位置：`codex-rs/codex-mcp/src/connection_manager.rs:760-779`。

配置项为 `tool_timeout_sec`。解析位置包括：

- `codex-rs/codex-mcp/src/rmcp_client.rs:334-336`
- `codex-rs/core/src/config/edit/document_helpers.rs:117-118`

用户中断时，MCP handler 所在的工具 task 仍受 `ToolCallRuntime` 的 cancellation select 控制。对于普通 MCP 工具，上层会 abort 调用 future 并生成 aborted output。

需要谨慎区分：取消 MCP 请求 future 能停止 Codex 继续等待，但不能证明远端 server 已经回滚或停止了业务操作。因此 Codex 的 turn-aborted 历史文案明确保留“工具可能已经部分执行”的不确定性。

### 4.6 Codex 不丢弃协议半截

取消工具后，Codex 生成 `AbortedToolOutput`：

```text
Wall time: 12.3 seconds
aborted by user
```

或：

```text
aborted by user after 12.3s
```

位置：

- 生成 aborted response：`codex-rs/core/src/tools/parallel.rs:237-258`
- 转成对应 call id 的工具输出：`codex-rs/core/src/tools/context.rs:277-304`

如果历史中仍出现 tool call 没有 output 的情况，context normalizer 会插入文本为 `aborted` 的合成输出：

- `codex-rs/core/src/context_manager/normalize.rs:1-127`

因此 Codex 的核心不变量是：保留 tool call 时，必须存在对应 tool output。

### 4.7 Turn 中断标记先持久化，再通知前端

工具取消收尾后，Codex 会写入模型可见的 `<turn_aborted>` 标记：

```text
The previous turn was interrupted on purpose.
Any running unified exec processes may still be running in the background.
If any tools/commands were aborted, they may have partially executed.
```

定义：`codex-rs/core/src/context/turn_aborted.rs:8-10`。

持久化顺序是：

1. `record_conversation_items()` 写入中断标记。
2. `flush_rollout()` 确保标记落盘。
3. 发送 `TurnAborted` 终态事件。
4. 再次 flush terminal event。

位置：`codex-rs/core/src/tasks/mod.rs:860-907`。

这个顺序避免前端收到“已中断”后立即重读会话，却看不到中断事实。

## 5. Claude Code 重建版：明确取消与提交新消息采用不同策略

### 5.1 明确按 Esc/Ctrl-C 会取消当前回合

REPL 的 `onCancel()` 会：

1. 标记本轮已中断。
2. 结束 query guard。
3. 保留已经流式生成的部分 assistant 文本。
4. 执行 `abortController.abort("user-cancel")`。
5. 清理当前 controller。

位置：`外部代码/claude-code-main/src/screens/REPL.tsx:2546-2637`。

因此明确取消并不是等待当前工具自然完成，而是向整个 query 和工具树传播 AbortSignal。

### 5.2 运行中提交新消息默认不会抢占所有工具

工具接口声明了：

```ts
interruptBehavior?(): 'cancel' | 'block'
```

语义为：

- `cancel`：停止工具并丢弃正常结果。
- `block`：保持工具运行，新消息等待。
- 未实现时默认 `block`。

位置：`src/Tool.ts:417-426`。

运行中提交新消息时，只有当前所有执行中工具都为 `cancel`，REPL 才调用：

```ts
abortController.abort('interrupt')
```

位置：`src/utils/handlePromptSubmit.ts:323-354`。

`SleepTool` 明确返回 `cancel`：`packages/builtin-tools/src/tools/SleepTool/SleepTool.ts:72-80`。

当前代码中 Bash 与 MCP 工具没有实现 `interruptBehavior()`，所以默认是 `block`。这意味着：

- 用户明确按 Esc：取消当前 turn。
- 用户只是在运行中提交新消息：Bash/MCP 通常继续运行，新消息进入队列。

这是 Claude Code 相比 Codex 更细的交互语义，不应被概括成“Claude Code 总是立即杀掉工具”。

### 5.3 每个工具拥有子 AbortController

`StreamingToolExecutor` 从 turn controller 创建 sibling controller，再为每个工具创建 child controller：

- turn → sibling：`src/services/tools/StreamingToolExecutor.ts:52-61`
- sibling → per-tool：`src/services/tools/StreamingToolExecutor.ts:321-352`

这样可以处理：

- 用户取消整个 turn。
- 一个 Bash 失败后取消同批兄弟工具。
- streaming fallback 时取消旧 executor 的在途工具。
- 权限弹窗拒绝时取消当前工具并向 turn 冒泡。

工具开始前和工具产生 update 后都会检查 abort 原因：

- 开始前合成取消结果：`StreamingToolExecutor.ts:303-318`
- 执行期间检测后合成取消结果：`StreamingToolExecutor.ts:359-371`

### 5.4 Bash 显式取消时杀进程树

Bash 把工具上下文中的 AbortSignal 传给 shell 执行器：

- `packages/builtin-tools/src/tools/BashTool/BashTool.tsx:768-816`
- `packages/builtin-tools/src/tools/BashTool/BashTool.tsx:1033-1050`

ShellCommand 监听 abort：

```ts
this.#abortSignal.addEventListener('abort', this.#boundAbortHandler, {
  once: true,
})
```

明确取消时，`#abortHandler()` 调用 `kill()`，最终通过 `treeKill(pid, 'SIGKILL')` 杀掉进程树：

- abort handler：`src/utils/ShellCommand.ts:186-193`
- tree kill：`src/utils/ShellCommand.ts:337-346`

但 `reason === "interrupt"` 时，ShellCommand 刻意不杀进程，准备让调用方把命令转为后台任务并保留部分输出：

```ts
if (this.#abortSignal.reason === 'interrupt') {
  return
}
```

这与前面的工具 `interruptBehavior` 设计一致：提交新消息和明确取消具有不同语义。

### 5.5 MCP 调用接收 AbortSignal，但默认 timeout 非常长

MCP 工具把 turn 的 signal 传入 MCP 调用：

```ts
signal: context.abortController.signal
```

位置：`src/services/mcp/client.ts:1845-1893`。

底层同时把 signal 和 timeout 交给 MCP SDK，并额外使用 `Promise.race` 做 timeout 兜底：

- `src/services/mcp/client.ts:3117-3205`
- 抽取后的 package 实现：`packages/mcp-client/src/execution.ts:56-89`

但默认 `MCP_TOOL_TIMEOUT` 是 `100_000_000ms`，约 27.8 小时：

- `src/services/mcp/client.ts:212-228`
- `packages/mcp-client/src/execution.ts:13-15`

这相当于默认依赖 AbortSignal，而不是依赖短超时。与 cb-agent 的差别仍然很大：cb-agent 既没有传单次调用 timeout，也没有把取消令牌转成 MCP AbortSignal。

连接级 cleanup 对 stdio MCP 使用信号升级：

```text
SIGINT → 等 100ms → SIGTERM → 再等约 400ms → SIGKILL
```

位置：`packages/mcp-client/src/connection.ts:298-370`。不过这段是连接关闭逻辑，不能等同于“每次工具调用取消都会重启 MCP server”。单次调用首先依赖 MCP SDK 对 AbortSignal 的处理。

### 5.6 中断时为每个 tool_use 补错误 tool_result

如果流式响应已经产生 `tool_use`，但用户在工具执行前或执行中取消，query 会消费 executor 的剩余结果，使 queued/in-progress 工具产生合成 `tool_result`：

- 流式阶段取消：`src/query.ts:1298-1338`
- 工具阶段取消：`src/query.ts:1669-1698`、`1778-1809`

没有 streaming executor 时，`yieldMissingToolResultBlocks()` 为每个 tool use 生成：

```ts
{
  type: 'tool_result',
  content: 'Interrupted by user',
  is_error: true,
  tool_use_id: toolUse.id,
}
```

位置：`src/query.ts:149-179`。

StreamingToolExecutor 则生成 `User rejected tool use` 等结构化错误结果，位置：`src/services/tools/StreamingToolExecutor.ts:180-231`。

query 最后还追加用户可见、模型可见的中断消息：

```text
[Request interrupted by user]
```

或：

```text
[Request interrupted by user for tool use]
```

定义和构造位置：

- `src/utils/messages.ts:208-214`
- `src/utils/messages.ts:548-562`

### 5.7 消息和 transcript 是增量写入，不等整个工具循环结束

QueryEngine 对 query generator yield 出来的 assistant/user 消息立即：

1. 追加到当前 messages。
2. 追加到 `mutableMessages`。
3. 调用 `recordTranscript()`。

位置：`src/QueryEngine.ts:700-747`、`768-811`。

因此中断产生的 tool_result 和 interruption message 会沿同一消息流进入 transcript，不需要等待一个完整的多轮 tool loop 最终成功收束。

此外，`ensureToolResultPairing()` 是最后一道防线：

- 缺 tool result 时插入合成错误结果。
- 孤立 tool result 会被移除。
- 重复 tool id/result 会被去重。

位置：`src/utils/messages.ts:5576-5820`。

## 6. cb-agent 当前行为

### 6.1 当前工具不会被通用取消

cb-agent 的 `ToolExecutor.execute()` 只在工具开始前检查 token：

- 批次提交前：`agent/executor.py:266-273`
- 串行每个工具开始前：`agent/executor.py:324-336`

一旦进入：

```python
result = self._runner(name, args)
```

就会同步等到工具返回，位置：`agent/executor.py:621-632`。

并行模式使用 `as_completed()` 等全部 future，且注释明确说明已提交工具不会被强制中止：`agent/executor.py:343-389`。

### 6.2 Tool loop 的取消只在边界生效

当前检查点包括：

- 每轮开始前：`agent/session.py:2377-2397`
- LLM 流返回后：`agent/session.py:2610-2625`
- 串行工具之间：`agent/executor.py:324-336`

工具批次返回后，tool loop 先追加所有工具消息并结束当前 round，到下一轮开头才再次检查取消：`agent/session.py:2711-2779`。

### 6.3 MCP 路径会无限等待

持久 MCP 路径：

```python
future = asyncio.run_coroutine_threadsafe(run_op(), self._persistent_loop)
return future.result()
```

位置：`tools/mcp_tools/mcptool.py:365-370`。

内部 FastMCP 调用也没有传 timeout：`tools/mcp_tools/client.py:278-289`。

因此当前工具既不轮询 cancel token，也没有 deadline。只要 MCP server 不返回，tool loop 就无法进入下一个取消检查点。

### 6.4 内存 history 是整轮提交，active checkpoint 是增量提交

`_tool_loop()` 原地修改 `messages`，整个循环返回后，`_chat_impl()` 才从 `commit_offset` 后提取新协议消息，一次性加入 `self.history`：

- offset：`agent/session.py:1639-1660`
- history commit：`agent/session.py:1705-1742`
- transcript commit：`agent/session.py:1752-1760`

运行期间，`active_turn.jsonl` 会增量记录完整 tool call 规划和已完成工具。崩溃恢复时，只保留已经具有 `tool_completed` 的配对调用，未完成调用被过滤：`agent/work_context.py:497-615`。

这能保证协议合法，但会丢失“工具已经开始、可能产生部分副作用”这一事实。

## 7. 行为对比

| 维度 | Codex | Claude Code 重建版 | cb-agent 当前 |
| --- | --- | --- | --- |
| 明确取消当前回合 | 立即取消 turn | 全局 AbortController | 只设置 CancelToken |
| 当前普通工具 | abort async task | 依赖 AbortSignal；生成合成结果 | 等工具自然返回 |
| Shell | TERM + 50ms + KILL 进程组 | 明确取消时 `treeKill(SIGKILL)` | 仅自身 timeout/KeyboardInterrupt；session cancel 不触达 |
| 运行中提交新消息 | 中断 active turn | 按 `interruptBehavior` 决定 cancel/block | busy，通常不能开始新请求 |
| MCP | 工具 task 可取消，另有 per-server timeout | 传 AbortSignal，另有超长默认 timeout | 无调用 timeout，无取消传播 |
| 并行工具 | 每个调用独立 cancellation select | 每工具 child controller | 已提交 future 全部自然结束 |
| 中断工具结果 | `aborted by user` 配对输出 | 合成 `is_error tool_result` | 只有尚未开始的串行工具有取消占位 |
| 缺失结果修复 | normalizer 插入 `aborted` | pairing repair 插入合成错误 | 恢复时删除未完成 tool call |
| turn 中断标记 | `<turn_aborted>`，先 flush 再发事件 | interruption user message | `Cancelled` 事件；历史没有统一中断标记 |
| 可能部分执行提示 | 明确提示 | 部分中断消息表达，但没有统一 unknown 状态 | 未完成调用恢复时被直接过滤 |

## 8. 对 cb-agent 的建议

### 8.1 明确取消应立即停止，不应同步等业务自然结束

对于用户明确点击取消或按 Ctrl-C，推荐采用 Codex 风格：

1. 立即设置 turn cancel token。
2. 同时取消当前 LLM stream。
3. 对当前工具调用执行 `cancel()`。
4. 等待一个很短的 teardown grace period，例如 100-500ms。
5. 仍未收尾时，终止其隔离进程或废弃 transport。
6. 为每个 tool call 生成终态 tool result。
7. 写入中断标记后释放 session busy。

这里等待的是资源清理，不是工具任务自然完成。

### 8.2 运行中提交新消息应增加工具级策略

可以借鉴 Claude Code，为工具增加：

```python
class InterruptBehavior(Enum):
    CANCEL = "cancel"
    BLOCK = "block"
    BACKGROUND = "background"
```

建议默认值：

- 纯读、无副作用、可重入工具：`CANCEL`。
- Bash 长任务：显式取消为 `CANCEL`；提交新消息可选 `BACKGROUND`。
- 文件写入和远程写操作：执行临界区内为 `BLOCK`，或取消后标记 `UNKNOWN`。
- MCP：默认 `CANCEL` 本地等待，但远端副作用状态必须允许标记为 `UNKNOWN`。

### 8.3 工具执行必须返回句柄，而不是只暴露同步 `run()`

建议引入：

```python
class ToolExecutionHandle:
    call_id: str

    def cancel(self, reason: str) -> None:
        ...

    def wait(self, timeout: float | None = None) -> ToolCallResult:
        ...
```

不同 runtime 分别实现：

- Bash：杀独立进程组。
- MCP：取消 coroutine；必要时关闭并重建连接。
- HTTP：关闭请求连接。
- 同进程 Python：协作轮询 token。
- 无法协作取消的 Python 工具：放入独立 worker process。

不能用“外层线程 future 超时”冒充强制取消，因为 Python 线程无法安全强杀，底层任务仍会继续运行。

### 8.4 引入明确的工具终态

建议状态至少包括：

| 状态 | 语义 |
| --- | --- |
| `completed` | 已得到可信结果 |
| `failed` | 已明确失败且执行结束 |
| `cancelled_before_start` | 从未开始，无副作用 |
| `cancelled` | 已确认底层停止 |
| `timed_out` | 超时且已确认停止 |
| `unknown` | 请求已经开始，但无法确认是否执行或是否产生副作用 |

尤其不能把远程写请求中断统一记录成 `cancelled`。连接断开只说明客户端停止等待，不说明服务端没有完成操作。

### 8.5 中断时不要丢弃 tool call；补齐终态 tool result

推荐正常受控中断时保留：

```text
assistant.tool_calls(call_id=X)
tool(call_id=X, status=cancelled/timed_out/unknown, is_error=true)
turn_aborted marker
```

例如：

```json
{
  "is_error": true,
  "status": "unknown",
  "cancelled": true,
  "message": "用户在工具执行期间中断了当前回合",
  "side_effect_state": "unknown",
  "retry_safety": "verify_before_retry"
}
```

这样下一轮模型既能看到协议合法的 call/result 配对，也不会误以为操作从未发生。

### 8.6 active turn 增加 started 与 terminal 事件

当前只有 `assistant_tool_calls` 和 `tool_completed`，建议扩展为：

```text
assistant_tool_calls
tool_started
tool_terminal(completed|failed|cancelled|timed_out|unknown)
turn_aborted
```

恢复规则建议为：

- 有 `tool_terminal`：恢复原 tool call 和对应 tool result。
- 只有规划、没有 `tool_started`：可合成 `cancelled_before_start`，或成对过滤。
- 有 `tool_started`、没有 terminal：合成 `unknown`，不能静默删除。
- 整个 turn 最后追加模型可见的中断标记。

这比当前“没有 tool_completed 就删除调用”更能反映真实副作用风险。

### 8.7 MCP 修复优先级最高

针对本次 CodeGraph 卡死，最低可行修复应包括：

1. `mcp.json` 支持 `tool_timeout_sec`。
2. 配置加载层保留并校验该字段。
3. `MCPClient.call_tool()` 把 timeout 传给 FastMCP。
4. `_run_via_persistent_client()` 使用短周期 `future.result(timeout=...)` 轮询 cancel token。
5. 取消时调用 `future.cancel()`。
6. 取消/超时后把当前 MCP connection 标记为不可复用。
7. stdio server 无法响应取消时，关闭 transport；必要时终止子进程并在下次调用前重连。
8. 返回配对的 `cancelled`、`timed_out` 或 `unknown` tool result。

## 9. 推荐状态流

```text
用户明确取消
    |
    v
设置 turn cancel token
    |
    +--> 关闭 LLM stream
    |
    +--> 取消 queued 工具
    |       -> cancelled_before_start
    |
    +--> 通知 running 工具 cancel
            |
            +--> 确认停止 -> cancelled
            |
            +--> deadline 到期并强杀成功 -> timed_out/cancelled
            |
            +--> 无法确认远端副作用 -> unknown

收集每个 call_id 的终态 tool result
    |
    v
写 active checkpoint / transcript
    |
    v
写 turn_aborted 标记并 flush
    |
    v
发 Cancelled/Done，释放 busy
```

## 10. 最终判断

对于“用户明确中断当前回合”，cb-agent 不应继续采用“等当前工具自然结束后才在下一个边界检查 token”的策略。Codex 和本地 Claude Code 重建版都证明，更成熟的实现会把取消信号传到工具运行时，并对 Bash、MCP、网络请求等可控资源采取实际终止动作。

但“立即中断”不等于“直接丢弃历史”：

- Codex 生成 aborted tool output，并持久化 turn-aborted 标记。
- Claude Code 为缺失的 tool use 生成错误 tool_result，并增量写入 transcript。
- 两者都优先维护工具调用协议的完整配对。

因此 cb-agent 最合理的方向是：**执行层立即取消，协议层补齐结果，持久化层记录不确定性**。对于已开始但不能确认副作用的工具，使用 `unknown`，而不是假装它没有执行，也不是把它误记成确定取消成功。

## 11. 2026-07-28 首期重构落地结果

本次实现没有保留两套主执行链。新的生产路径统一使用
`Tool.run_with_context(parameters, context)`；旧 `Tool.run()` 只作为第三方工具和
直接调用的兼容入口。旧 `tool_completed` 同样只保留读取兼容，新 journal 不再写入。

### 11.1 取消与终态协议

- `CancellationContext` 记录原因、发生时间、deadline、父子传播和运行时回调；
  `CancelToken` 是兼容别名。
- `ToolExecutionContext` 为每次调用携带 turn、round、call ID 和子取消上下文。
- 工具终态统一为 `completed`、`failed`、`cancelled_before_start`、`cancelled`、
  `timed_out`、`unknown`，并独立记录副作用确定性。
- Gateway 的取消 RPC 只返回 `accepted=true, completed=false`；整个回合只有在工具
  终态和 transcript 已提交后才发最终 `Cancelled` 事件。

### 11.2 Bash 与 MCP

- Bash 前台进程启动后立即注册取消回调。用户取消或 deadline 到期时向独立进程组
  发送 TERM，50ms 后升级为 KILL，执行线程统一回收管道并返回部分输出。
- MCP 的调用、连接建立和同 server 调用锁等待均以 50ms 边界观察取消。持久客户端
  不再出现无参数 `future.result()`；取消会调用 `future.cancel()` 并使连接失效。
- `mcp.json` 的 `tool_timeout_sec` 已保留并校验；全局默认 120 秒，支持
  `CB_AGENT_TOOL_TIMEOUT_SEC`、server 级覆盖以及 Bash 单次毫秒级覆盖。

### 11.3 历史与恢复

新 active-turn 事件为：

```text
turn_started
assistant_tool_calls
tool_started
tool_terminal
assistant_final
turn_aborted
```

中断恢复不再删除未完成调用：已开始无终态合成为 `unknown`，已规划未开始合成为
`cancelled_before_start`。每个保留的 `assistant.tool_calls` 都有同 call ID 的 tool
结果，末尾追加模型可见但 UI 隐藏的 `<turn_aborted>` 标记。

### 11.4 明确边界

首期只对 Bash 和 MCP 等外部运行时承诺主动终止。普通进程内 Python 工具仍采用
协作取消；如果工具不检查上下文，系统会等待其返回，不会遗留一个仍可能产生副作用
的后台线程。要让任意 Python 工具都可硬停，需要后续引入独立工作进程隔离。
