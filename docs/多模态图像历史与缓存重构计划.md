## 1. 结论先行

用户对当前缓存问题的判断是正确的。

当前 CbAgent 在一次完整 `chat()` 内，会让用户附件的 data URL/base64 一直留在同一个 `messages` 数组中，因此同一次 tool loop 的第 2、3、4 次模型调用仍然拥有稳定的请求前缀。它不会在 tool loop 的第一轮结束后立刻把图片替换成文本。

但是，当这次完整 `chat()` 结束时，CbAgent 提交到 `self.history` 的不是模型实际见过的多模态 user 消息，而是 `history_text` 文本摘要。下一次用户对话重新构造请求时，上一轮原本的：

```text
user(text + image_url:data:image/...;base64,...)
```

已经变成：

```text
user(text + 图片附件摘要)
```

因此，上一轮图片消息之后的 assistant/tool/final answer 虽然内容未变，但它们在新请求中的前置字节已经变化。对于按最长公共前缀工作的 provider Prompt Cache，缓存只能命中到该图片消息之前。用户给出的“只剩 1 可命中，原来的 2+3 需要重新 prefill”的推导成立。

`filepath` 也没有覆盖 base64。当前实现只是下一轮不再构造旧图片 data URL，改用文本摘要；路径只作为摘要元数据的一部分。即使未来内部 history 改存 filepath，如果发给 provider 时不能确定性地还原出与首次请求完全相同的图片内容块，缓存前缀仍然会断裂。

目标方案应采用以下原则：

1. 模型已经见过的逻辑消息，在普通追加对话中不可变。
2. history 不必保存 raw base64，但必须保存可确定性还原原图的 `ImageRef`。
3. 每次发送给 provider 时，由 adapter 把同一个 `ImageRef` 还原为相同的 data URL、原生图片块或稳定的 provider 文件引用。
4. `load_image` 的图片必须成为正式的工具结果/逻辑历史，不能只是当前请求的临时 `pending_images`。
5. compact 是允许重写 history 的显式边界；普通用户回合和 tool loop 只能追加。
6. compact 的摘要输入应去掉 base64，但 compact 后保留的最近完整回合仍应保留 `ImageRef`。

这套方案同时吸收了 Codex 的“正式 ResponseItem + append-only history + Responses 增量游标”和 Claude Code 的“图片属于正式 messages/tool_result + compact 摘要视图去图片 + 保留尾部原样拼回”设计。

## 2. 术语和边界

为了避免“轮”这个词混淆，本文使用四个明确术语：

| 术语 | 含义 | 当前代码中的近似边界 |
| --- | --- | --- |
| 用户回合（user turn） | 用户提交一次输入，到 Agent 给出最终回答或中止 | 一次完整 `AgentSession.chat()` / `_chat_impl()` |
| 工具轮（tool round） | 模型 think 一次，可能生成一批 tool calls，执行并回灌结果 | `_tool_loop()` 中一次 `round_idx` |
| Provider 请求 | 实际调用一次模型 API | 每次 `llm.think()`；compact 摘要请求另算 |
| Durable history | 下一用户回合、重启恢复和 compact 可读取的正式逻辑历史 | 当前 `self.history` + transcript/compact 持久化 |

用户问题中的“执行完一个完整 tool loop 的下一轮对话”属于下一个用户回合；“tool loop 的一次循环”属于下一个工具轮。

当前图片替换问题发生在前者，不是后者：

```text
用户回合 N
  工具轮 1：旧 history + 当前 user(base64)
  工具轮 2：旧 history + 当前 user(base64) + assistant/tool
  工具轮 3：旧 history + 当前 user(base64) + assistant/tool + assistant/tool
  完成 chat()：提交 user(文本摘要) + assistant/tool/final

用户回合 N+1
  第一次请求：旧 history + user(上一轮文本摘要) + ... + 当前 user
                         ^ 与上一轮实际发送的 base64 消息不同，缓存从这里断开
```

## 3. 当前 CbAgent 的真实行为

### 3.1 用户附件被拆成两份内容

`agent/multimodal_input.py` 中的 `ProcessedMultimodalPrompt` 同时返回：

- `request_content`：当前用户回合发给模型的内容；视觉模型下包含 `image_url` data URI。
- `history_text`：准备写入 history/transcript/compact 的文本摘要和附件元数据。

视觉图片在 `_process_one_attachment()` 中读取文件、编码 base64，并追加到 `request_parts`。同一处明确写着“跨轮历史只保留摘要”。

`agent/session.py::_chat_impl()` 随后分别使用：

```text
request_content   -> _build_chat_messages() -> 当前 tool loop 的 messages
history_user_text -> turn_prefix_messages   -> 用户回合结束后的 self.history
```

这不是“base64 后来被 filepath 覆盖”，而是从一开始就维护了请求版和持久化版两份不同消息。

### 3.2 同一个 tool loop 内不会替换初始附件

`_tool_loop()` 在一个 `messages` list 上原地追加 assistant、tool 和最终 assistant。每个工具轮开始时调用 `llm.think(messages, ...)`，不会重新用 `history_text` 构造旧 user 消息。因此：

- 用户附件 base64 在同一次 tool loop 内保持不变。
- 后续工具轮理论上可以命中前一工具轮的完整前缀。
- `commit_offset` 只标记本次用户回合新增协议消息的提取起点，不会在普通工具轮之间改写图片。

例外是 mid-turn compact。当前实现会在窗口压力达到阈值时重写 `messages`。这本来就是一个预期的缓存重建边界，但当前图片的 request-only 语义使其存在丢图和重放不完整风险，详见第 8 节。

### 3.3 完整用户回合结束后，旧图片消息变成文本

tool loop 完成后，`_chat_impl()` 会把 `turn_prefix_messages` 和 `commit_offset` 之后抽出的 assistant/tool 消息提交到 `self.history`。

关键问题是：

- `turn_prefix_messages` 中的 user 内容是 `history_user_text`，不是 `request_content`。
- `_extract_protocol_messages()` 只提取 assistant 和 tool，明确跳过 tool loop 中新增的 user 多模态消息。

因此，下一用户回合的 `_sliced_history_dicts()` 无法恢复上一轮模型实际看到的图片消息。

### 3.4 `load_image` 当前通过临时缓冲注图

当前 `load_image` 的视觉分支执行以下流程：

```text
load_image.run()
  -> 本地文件转 data URL，或直接保留 http(s) URL
  -> queue_image(call_id="", ...)
  -> 工具本身返回纯文本 JSON

AgentSession 执行完同一批工具
  -> 先追加 role=tool 文本结果
  -> drain_images()
  -> 再合成一条 role=user 的图片消息
  -> 下一工具轮模型看到图片
```

该方案有五个结构性问题：

1. `call_id` 被写成空字符串，图片与触发它的 tool call 失去正式关联。
2. 图片只存在于进程内 `ContextVar` 缓冲和当前 `messages`。
3. 合成 user 图片消息被 `_extract_protocol_messages()` 跳过，不进入 durable history。
4. 崩溃恢复、会话重启、下一用户回合都不能重放这张图片。
5. `MessageLogger` 当前接收原始 `messages`，实际可能把 base64 原样写入日志，与模块注释声明的安全边界不一致。

### 3.5 当前 token 估算并不等于视觉 token 估算

`_estimate_request_tokens()` 会用 `sanitize_multimodal_payload()` 把 data URI 替换成短占位符，再按 JSON 文本计数。这避免了错误地把 base64 字符数当文本 token，但也意味着运行中请求估算没有统一累加每张图片按尺寸/detail 产生的视觉 token。

用户附件预处理阶段已有 `_estimate_native_image_tokens()`，但历史、`load_image`、compact retained tail 和 provider 请求估算还没有共享同一套视觉成本模型。

## 4. 用户缓存例子的精确结论

假设稳定系统提示为 `S`，上上轮历史为 `H0`，用户回合 N 发送图片，tool loop 产生 `A1/T1/A2`：

当前用户回合 N 的最后一次 provider 请求近似为：

```text
[S, H0, U1(text + BASE64_X), A1(tool_call), T1(result), A2(final)]
```

当前提交后的 logical history 实际为：

```text
[H0, U1(text + image summary/path/hash), A1(tool_call), T1(result), A2(final)]
```

用户回合 N+1 再发一张图片，请求变成：

```text
[S, H0, U1(text + image summary/path/hash), A1, T1, A2, U2(text + BASE64_Y)]
```

与上一请求的最长公共前缀只到 `S + H0`。`U1` 发生变化，所以 `A1/T1/A2` 即使字节完全一样，也位于变化点之后，需要重新计算。

目标实现应变成：

```text
内存/磁盘逻辑历史：
[H0, U1(text + ImageRef(X)), A1, T1, A2]

用户回合 N+1 序列化给 provider：
[S, H0, U1(text + BASE64_X), A1, T1, A2, U2(text + BASE64_Y)]
```

只要 `ImageRef(X)` 每次确定性还原为完全相同的 `BASE64_X` 和相同 JSON 结构，`S + H0 + U1 + A1 + T1 + A2` 就仍是稳定缓存前缀。

需要区分两种成本：

- Prompt prefill 成本：稳定前缀可以由 provider cache 或 `previous_response_id` 避免重复计算。
- 网络传输成本：Chat Completions 每次仍可能需要重复上传 base64 请求体；只有 Responses 增量、provider 文件 ID 或稳定远程对象引用才能避免重复传输。

所以 `ImageRef` 直接解决 history 可重放和 Prompt Cache 稳定性；Responses adapter 是进一步解决重复传输的重要阶段。

## 5. Codex 与 Claude Code 的处理方式

> 外部目录中的 `claude-code-main` 是逆向/反编译实现，不能视为 Anthropic 官方源码。本文只把它作为可观察的架构样本，不依赖其私有细节作为协议保证。

### 5.1 Codex

相关实现位于：

- `外部代码/codex-main/codex-rs/protocol/src/user_input.rs`
- `外部代码/codex-main/codex-rs/protocol/src/models.rs`
- `外部代码/codex-main/codex-rs/core/src/context_manager/history.rs`
- `外部代码/codex-main/codex-rs/core/src/tools/handlers/view_image.rs`
- `外部代码/codex-main/codex-rs/core/src/client.rs`
- `外部代码/codex-main/codex-rs/core/src/compact.rs`
- `外部代码/codex-main/codex-rs/core/src/compact_remote_v2.rs`

可借鉴的不变量：

1. 用户图片作为正式 `InputImage`/`ResponseItem` 进入上下文和 rollout，而不是下一回合替换为另一条摘要消息。
2. `view_image` 返回带 `InputImage` 的原生 `FunctionCallOutput`，保留 call id 和工具结果归属。
3. 请求在满足“旧请求严格为新请求前缀、模型/指令/工具/缓存键均一致”时使用 `previous_response_id` 做增量续接。
4. `prompt_cache_key` 默认使用 thread ID，保证同一会话缓存归属稳定。
5. 普通 history 操作以 append 为主；compact/rollback 才是允许的重写点。

Codex 的 compact 图片语义也很关键：

- 本地文本摘要路径的 `content_items_to_text()` 直接忽略 `InputImage`，不会把 data URL塞入摘要文本。
- remote compact v2 对预算内保留消息进行 clone；保留消息内的 `InputImage` 仍原样保留。
- 代码明确统计 `retained_image_count`，并有测试验证 retained history 中的图片没有消失。

也就是说，Codex 区分了“被摘要覆盖的旧图片”和“仍处于保留尾部的图片”。前者不进入文本摘要，后者继续作为正式图片内容存在。

### 5.2 Claude Code

相关实现位于：

- `外部代码/claude-code-main/src/query.ts`
- `外部代码/claude-code-main/src/QueryEngine.ts`
- `外部代码/claude-code-main/src/services/api/claude.ts`
- `外部代码/claude-code-main/packages/builtin-tools/src/tools/FileReadTool/FileReadTool.ts`
- `外部代码/claude-code-main/src/services/compact/compact.ts`
- `外部代码/claude-code-main/src/utils/toolResultStorage.ts`

可借鉴的不变量：

1. 用户图片 `{type: image, source: {type: base64, ...}}` 是正式 messages/transcript 的一部分。
2. 工具循环按 `old messages + assistant messages + tool results` 追加，已发送过的工具结果不在下一轮替换。
3. FileRead 读取图片时，图片直接成为带 `tool_use_id` 的 `tool_result.content.image`，而不是旁路临时消息。
4. Prompt cache 标记放在最新的可缓存内容末尾，旧消息本身不改写。
5. 对大工具结果可以把 UI payload 外置，但模型已经见过的逻辑 tool result 仍保持稳定或使用稳定引用。

Claude Code 的 compact 逻辑尤其适合 CbAgent：

- `stripImagesFromMessages()` 只构造给“摘要模型”的派生视图，把普通用户图片和 `tool_result` 内图片替换为 `[image]`/`[document]`。
- `messagesToKeep` 是独立的保留尾部，最终由 `buildPostCompactMessages()` 原样拼回。
- compact 后顺序近似为 `boundary + summary + messagesToKeep + attachments + hookResults`。

因此，删除图片只发生在 compaction view，不是对 durable history 的就地修改。

### 5.3 对比结论

| 设计点 | 当前 CbAgent | Codex | Claude Code | CbAgent 目标 |
| --- | --- | --- | --- | --- |
| 用户图片跨轮 | 替换为文本摘要 | 正式 InputImage | 正式 image block | `ImageRef` 持久化，发送时还原 |
| 工具读图 | 临时 user 消息 | 原生 function output image | tool_result image | 中立 ToolResultImage，adapter 展开 |
| 普通 tool loop | 基本追加 | 追加 | 追加 | 严格追加和冻结 |
| Prompt Cache | 依赖全量前缀，旧图处断裂 | cache key + previous response | cache_control + 不改旧消息 | provider 能力分层 |
| compact 摘要输入 | 当前可能直接结构化发送 history | 旧图不转文本 | 派生视图去图片 | `compaction_view` 去 raw 图片 |
| compact 保留尾部 | 当前历史本身没有正式图片 | 保留图片 | 保留原消息 | 保留 `ImageRef` |
| 持久化 | 文本替代图像 | rollout 可重放 | transcript 可重放 | ref 可重放，raw base64 不落 JSONL |

## 6. 目标架构总览

```text
用户附件 / load_image / 未来截图工具
                  │
                  ▼
        MediaIngestor（校验、解码、规范化）
                  │
                  ▼
     MediaBlobStore（内容寻址、原子落盘、去重）
                  │
                  ▼
 ImageRef(blob_id, sha256, mime, dimensions, detail, ...)
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
 Logical History       Transcript / Active Turn
 （不可变内容项）        （只保存 ImageRef）
        │
        ▼
 ProviderSerializer / ProviderAdapter
        ├─ Chat Completions -> image_url data URI + 必要的合成 user bridge
        ├─ Responses        -> input_image / function_call_output + previous_response_id
        └─ Anthropic        -> image block / tool_result image + cache_control
```

整个系统需要分成三个表示层，不能继续混用同一个 dict：

1. 逻辑表示：provider 无关，存 `TextPart`、`ImageRefPart`、`ToolCallItem`、`ToolResultItem`。
2. 持久化表示：逻辑表示的 JSON 版本，只包含引用和元数据，不包含 raw base64。
3. 传输表示：在每次请求边界由 provider adapter 临时生成，允许出现 base64，但不得回写逻辑 history。

## 7. 核心数据模型

### 7.1 `ImageRef`

建议新增 `core/media.py`：

```python
@dataclass(frozen=True)
class ImageRef:
    schema_version: int
    blob_id: str
    sha256: str
    mime_type: str
    byte_size: int
    width: int | None
    height: int | None
    detail: str | None
    canonicalization_version: int
    file_name: str | None
    source_kind: str
```

字段约束：

- `blob_id` 建议直接使用 `sha256:<hex>`，或者使用独立 ID 并强校验 sha256。
- `file_name`、原路径、URL 仅是展示和审计元数据，不能作为内容身份。
- `detail` 属于模型语义的一部分；从 `auto` 改成 `high` 会改变视觉 token 和结果，应进入稳定序列化。
- `canonicalization_version` 防止未来升级缩放/转码算法后，用同一个 ref 名称产生不同字节。
- 对本地文件必须在首次接收时复制到 blob store；后续源文件被覆盖不能改变旧消息。

### 7.2 内容项和逻辑消息

建议将 `core/message.py` 从 `List[Dict[str, Any]]` 逐步升级为带判别字段的内容项：

```python
TextPart(text: str)
ImageRefPart(image: ImageRef)
DocumentRefPart(document: DocumentRef)  # 可后续扩展

LogicalMessage(
    id: str,
    role: user | assistant | tool | system,
    content: tuple[ContentPart, ...] | str | None,
    tool_calls: ...,
    tool_call_id: str | None,
    metadata: ...,
)
```

第一阶段可保留现有 `Message`，只新增一种内部内容块：

```json
{
  "type": "image_ref",
  "image_ref": {
    "blob_id": "sha256:...",
    "mime_type": "image/png",
    "detail": "auto"
  }
}
```

不要把 `image_ref` 直接传给 OpenAI SDK；只能由 provider serializer 展开。

### 7.3 `ToolExecutionResult`

当前 `ToolCallResult.result` 只能是字符串，不足以表达图片。建议扩展为：

```python
@dataclass(frozen=True)
class ToolModelResult:
    text: str
    content: tuple[ContentPart, ...] = ()

@dataclass
class ToolCallResult:
    call_id: str
    name: str
    arguments: dict[str, Any]
    model_result: ToolModelResult
    display_payload: Any | None
    # 其余状态字段保持不变
```

其中：

- `text` 是所有 provider 都能处理的说明和错误信息。
- `content` 可包含 `ImageRefPart`，是真正发给模型的内容。
- `display_payload` 只用于 UI，不进入模型上下文，也不应影响缓存前缀。
- result cap 只裁剪文本或把大文本外置，不能删除/偷偷替换图片内容项。

### 7.4 不可变规则

每条进入 provider 请求的逻辑消息应拥有稳定 `message_id` 和内容摘要：

```text
content_digest = sha256(canonical_json(logical_message))
```

消息一旦标记 `sent=True`：

- 普通用户回合只能在尾部追加。
- 不允许把 `ImageRefPart` 改成摘要文本。
- 不允许把完整 tool result 改成另一个文本 stub。
- 不允许因源文件变化重新读取出不同字节。
- 只有 compact、rollback、clear、显式迁移可以创建新的 history generation。

开发模式可在每次 provider 请求前验证：旧前缀的 `message_id + content_digest` 是否与上一次相同；发现中间改写直接记录错误。

## 8. Compact 的完整设计

这是本次重构中最重要的部分之一。

### 8.1 Compact 必须区分三个集合

一次 compact 不能把整个 history 先改成文本再处理。应先按完整用户回合和工具协议边界切分成：

```text
summarized_prefix  = 被摘要替代的旧回合
retained_tail      = 预算内保留的最近完整回合
active_turn_items  = 当前仍在执行的用户回合（仅 mid-turn 存在）
```

三者语义不同：

- `summarized_prefix`：生成摘要后从 active history 中移除。
- `retained_tail`：逻辑消息原样保留，图片仍是 `ImageRef`。
- `active_turn_items`：mid-turn 时绝对不参与摘要，原样接在 compact 后历史尾部。

compact 后建议顺序为：

```text
[compact boundary, summary of summarized_prefix, retained_tail, active_turn_items]
```

摘要必须只覆盖 `summarized_prefix`，不要像当前实现那样先摘要整个 source 再把一部分原消息重复保留，否则 summary 与 retained tail 语义重复，且难以判断旧图片是否已被摘要覆盖。

### 8.2 `compaction_view`：只给摘要模型的派生视图

新增纯函数：

```python
build_compaction_view(messages: Sequence[LogicalMessage]) -> list[dict]
```

转换规则：

- 普通 user 图片：替换成文本标记。
- `load_image`/其他 tool result 中的图片：在对应 tool result 内替换成文本标记。
- 不读取 blob，不生成 base64，不让摘要 provider 拉远程 URL。
- 文本、tool call 名称、参数、call id、错误状态正常保留。
- display-only payload 和本地绝对路径按日志策略脱敏。

建议标记格式：

```text
[image: file=diagram.png, sha256=ab12..., mime=image/png, size=1600x900, source=user_attachment]
```

工具图片建议额外保留关联：

```text
[tool image: tool=load_image, call_id=call_123, file=screen.png, sha256=cd34..., size=1280x720]
```

这使摘要模型知道“这里曾有图片”，但不会让 base64 挤占摘要窗口。若模型之前已经对图片给出文字分析，摘要模型可从后续 assistant 文本中总结视觉结论。

### 8.3 Retained tail 中图片如何处理

`retained_tail` 不能调用 `build_compaction_view()`，而应保留原始 `ImageRefPart`。compact 安装后，下一次正常 provider 请求由 adapter 再还原同一图片。

因此 compact 后的磁盘结构可能是：

```json
[
  {"kind": "compact_boundary", "generation": 4},
  {"role": "user", "kind": "context_compaction", "content": "...summary..."},
  {
    "role": "user",
    "content": [
      {"type": "text", "text": "请看这张图"},
      {"type": "image_ref", "image_ref": {"blob_id": "sha256:..."}}
    ]
  },
  {"role": "assistant", "content": "..."}
]
```

raw base64 不在文件中，但图片语义没有丢失。

### 8.4 Mid-turn compact

当前实现会把 `self.history + turn_prefix + inflight` 一起交给 `compact_context()`，并把 request-only user 图片另行回挂。这会造成两个问题：

1. 用户本轮最初附件位于 `commit_offset` 之前，不属于 `_extract_request_only_inflight_messages()`，compact 重建后可能丢失。
2. 当前活动工具链被摘要后继续执行，容易拆散 assistant tool call、tool result、图片 bridge 和后续 assistant 的协议关系。

目标语义应改为：

1. tool loop 开始时创建 `ActiveTurn`，其中保存当前 user 的完整逻辑消息，包括 `ImageRef`。
2. 每次 assistant/tool/load_image 结果都立即追加到 `ActiveTurn.items` 并写 active checkpoint。
3. mid-turn 达到 soft limit 时，只 compact 已提交 durable history。
4. compact 完成后重新组装：`system + compacted durable history + ActiveTurn.items`。
5. `ActiveTurn.items` 全部保持相同 message id、内容摘要和图片 ref。
6. 如果“compact 后 durable history + 当前 active turn”仍超过 hard limit，必须停止当前回合并明确报错，不能把活动工具协议链压成摘要后假装继续。

这意味着 active turn 自身过大的情况需要在图片数量、图片分辨率、单工具输出和工具轮上限处提前治理。

### 8.5 图片 token 预算

不能按 `ImageRef` JSON 的字符数统计，也不能像当前 sanitize 路径一样把每张图当成近乎零成本。

统一估算函数应返回：

```text
request_tokens = text_tokens
               + tool_schema_tokens
               + sum(image_visual_tokens(width, height, detail, provider, model))
```

要求：

- 用户附件和 `load_image` 使用同一估算器。
- retained tail 的图片继续计入视觉 token。
- `compaction_view` 中的图片只按标记文本计数，因为摘要请求不发送原图。
- provider usage 返回实际 input/cached tokens 后，继续使用现有校准机制，但视觉 token 应单独记录，避免文本校准因图片样本发生偏移。

### 8.6 Compact 与缓存

compact 本身必然改变旧 history，是合理且可观测的缓存失效边界。应新增：

- `history_generation`：普通追加不变；compact/rollback/clear 后加一。
- `compaction_id` 和 `covered_message_ids`：便于审计摘要覆盖范围。
- Responses cursor reset：generation 变化后清空 `previous_response_id`。
- Prompt cache 事件：记录 `cache_reset_reason=compact`，不要把正常重建误报为缓存回归。

目标不是让 compact 后继续命中 compact 前的旧前缀，而是保证：

- 普通用户回合不会因为旧图片被替换而意外失效。
- compact 只造成一次有意的缓存重建。
- compact 后的新 generation 再次保持 append-only。

## 9. `load_image` 的完整设计

### 9.1 删除 `pending_images` 作为最终架构

`tools/tools/pending_images.py` 可以在迁移期保留兼容，但最终应删除。工具结果不应通过进程全局/上下文旁路传递额外模型内容。

新流程：

```text
模型调用 load_image(call_id=call_123, path=...)
  -> 工具校验路径/URL
  -> MediaIngestor 读取并规范化图片
  -> MediaBlobStore.put() 返回 ImageRef
  -> ToolCallResult(
       call_id="call_123",
       model_result={text: "图片加载成功", content: [ImageRefPart]},
       display_payload=...
     )
  -> AgentSession 把同一个结构化结果追加到 ActiveTurn
  -> ProviderAdapter 按协议展开
```

### 9.2 Chat Completions adapter

许多 OpenAI-compatible Chat Completions 服务不允许 `role=tool` 中包含 `image_url`。兼容展开应为稳定的两条消息：

```text
assistant(tool_call id=call_123 name=load_image)
tool(tool_call_id=call_123, content="图片已加载：screen.png")
user(metadata.kind=tool_media_bridge,
     metadata.tool_call_id=call_123,
     content=[text说明, image_ref -> image_url:data URI])
```

关键要求：

- 这条合成 user 消息是正式逻辑历史成员，不是 request-only 临时消息。
- 必须保留真实 `call_id`，不能再用 `call_id=""`。
- 合成消息的 `message_id`、文字模板、图片顺序和 JSON 字段顺序必须确定。
- 下一用户回合、重启恢复和 retained compact 都能重新生成同一传输消息。
- `_extract_protocol_messages()` 必须允许提交 `metadata.kind=tool_media_bridge` 的 user 消息，或者更彻底地从 `ActiveTurn.items` 统一提交，不再按 role 白名单逆向提取。

### 9.3 Responses adapter

当 provider 支持 Responses API 时，优先使用原生结构：

```text
function_call_output(
  call_id=call_123,
  content=[input_text, input_image]
)
```

这更接近 Codex：

- 图片属于工具输出本身。
- 不需要伪造额外 user 消息。
- 可以结合 `previous_response_id` 只发送新增 items。
- history 中仍保存同一个 provider-neutral `ToolResultItem`，而不是保存 Responses SDK 对象。

### 9.4 Anthropic adapter

当 provider 支持 Anthropic Messages 时，展开为：

```text
user.content = [
  {
    "type": "tool_result",
    "tool_use_id": "call_123",
    "content": [
      {"type": "text", "text": "图片已加载"},
      {"type": "image", "source": {"type": "base64", ...}}
    ]
  }
]
```

这更接近 Claude Code 的 FileRead 图片处理。adapter 负责 `cache_control`，不能把缓存字段混进逻辑 history。

### 9.5 非视觉模型

非视觉模型继续使用 OCR，但也应返回统一结构：

```text
ToolModelResult(text=<OCR 文本>, content=())
```

OCR artifact 可像现有附件文本一样内容寻址落盘。切换到视觉模型后，不应悄悄把旧 OCR 工具结果替换成原图；旧消息已经发送过，必须保持原样。若需要看原图，应发起新的 `load_image` 调用。

### 9.6 URL 图片

当前视觉分支直接把 http(s) URL 透传给 provider，存在内容漂移、过期和服务端网络差异。为了可重放和缓存稳定，建议：

1. 使用受限下载器获取一次内容，执行 DNS/IP/重定向/大小/MIME 安全校验。
2. 写入 `MediaBlobStore` 后生成 `ImageRef`。
3. 后续不再依赖 URL 当前内容。
4. 原 URL 只作为审计 metadata，日志中按策略脱敏 query 参数。

若某 provider 必须使用 URL，则 adapter 应使用由本地 blob 上传得到的稳定对象 URL/文件 ID，而不是继续引用可能变化的源 URL。

## 10. MediaBlobStore 设计

### 10.1 目录布局

建议会话项目下使用：

```text
.cbagent/media/
  blobs/
    sha256/
      ab/
        abcdef...              # 规范化后的原始字节
  metadata/
    sha256/
      ab/
        abcdef....json         # MIME、尺寸、版本等，不含 base64
  tmp/                         # 原子写临时文件
```

写入流程：

1. 流式读取并执行大小上限。
2. 校验真实文件签名，不只相信扩展名。
3. 解码图片，处理 EXIF orientation。
4. 按明确版本执行可选缩放/转码；不要每次请求重新处理。
5. 对最终字节计算 SHA-256。
6. 临时文件写完并 `fsync` 后原子 rename。
7. 已存在同 hash 时复用，不重复落盘。

### 10.2 确定性序列化

对同一个 blob，Chat adapter 必须固定生成：

```text
data:<normalized mime>;base64,<RFC 4648 standard base64 without line breaks>
```

以下内容都必须稳定：

- MIME 大小写和别名，例如统一 `image/jpeg`。
- base64 alphabet、padding 和换行策略。
- 图片 content part 的字段结构。
- text part 与 image part 的顺序。
- `detail` 的默认值是否显式发送。
- Chat 合成 bridge 的说明文字。

缓存测试不能只比较语义对象，应比较 provider request 的 canonical JSON 字节前缀。

### 10.3 生命周期和垃圾回收

blob 引用来源包括：

- active history
- active turn checkpoint
- compact replacement
- transcript 审计记录
- pending user 输入
- 可恢复的失败/中止回合

GC 不能只扫描当前 `self.history`。建议先做 mark-and-sweep：

1. 扫描所有会话持久化记录收集 `blob_id`。
2. 加入未过期 active/pending 引用。
3. 对无引用且超过宽限期的 blob 执行删除。
4. 默认不因为 compact 立即删除被摘要覆盖的旧图，因为 transcript 仍可能需要恢复/审计；可按 retention policy 清理。

## 11. History、持久化与日志

### 11.1 Durable history 保存逻辑事实

history 的定义应改为：

> 模型实际见过的逻辑消息序列，而不是为了节省磁盘而制作的另一份语义近似文本。

“不保存 raw base64”与“保存真实多模态 history”并不冲突。磁盘保存 `ImageRef`，provider 请求临时展开即可。

### 11.2 Active turn checkpoint

`begin_active_turn()` 当前只保存文本 user query。应升级为：

```text
begin_active_turn(turn_id, user_message=<含 ImageRef 的完整逻辑消息>)
append_active_item(assistant/tool/tool_media_bridge/...)
commit_active_turn()
```

这样进程在以下时点崩溃都能恢复：

- 用户图片已接收但第一次 think 未完成。
- `load_image` 已落 blob、tool 文本结果已生成，但下一次 think 尚未开始。
- 图片已被模型看见，最终回答尚未提交。
- mid-turn compact 已完成但 active turn 仍在继续。

### 11.3 Transcript

`agent/work_context.py::_message_to_persist_payload()` 已支持 user content list，是良好的迁移基础。需要新增：

- `image_ref` schema 校验和往返恢复。
- `message_id`、`content_digest`、`history_generation`。
- tool image 关联字段。
- legacy payload 迁移版本。

transcript 中禁止写：

- `data:image/...;base64,...`
- Anthropic image `source.data`
- provider 临时上传凭证/签名 URL

### 11.4 MessageLogger

当前 `MessageLogger.log(messages)` 直接写入完整 request dict，必须改为显式日志投影：

```python
log_payload = ProviderPayloadRedactor.redact(provider_payload)
```

图片记录为：

```json
{
  "type": "image",
  "blob_id": "sha256:...",
  "mime_type": "image/png",
  "byte_size": 12345,
  "dimensions": [1600, 900],
  "encoded_chars": 16460,
  "data": "<omitted>"
}
```

redactor 必须覆盖：

- OpenAI `image_url.url` data URI。
- Anthropic `source.data`。
- Responses `input_image.image_url`。
- tool result 内嵌图片。
- 任意深层 dict/list 中的 `data:*;base64,`。

日志 redaction 和 token estimation 不能共用一个“修改真实 messages”的函数；两者都应返回副本，并有“不改变输入对象”的测试。

## 12. Provider 与 Prompt Cache 分层

### 12.1 Provider capability

建议为 active model 增加结构化能力：

```text
supports_images
supports_image_in_tool_result
supports_responses_api
supports_previous_response_id
supports_prompt_cache_key
supports_anthropic_cache_control
supports_provider_file_id
```

不要只用当前 `image_ability: bool` 决定所有协议行为。

### 12.2 Chat Completions

第一阶段继续支持现有 OpenAI-compatible Chat Completions：

- 每次发送全量 logical history 的 provider 展开结果。
- 依靠稳定系统提示、稳定工具 schema、冻结旧消息和确定性图片编码命中 provider 前缀缓存。
- 不假定所有中转站都支持显式 cache key。
- 网络上仍会重复发送 base64，这是协议限制而不是 history 设计失败。

### 12.3 Responses

贴近 Codex 的关键阶段：

- `thread_id` 作为稳定 `prompt_cache_key`。
- 保存 `last_response_id`、上一请求的 generation 和 provider config fingerprint。
- 只有以下条件同时满足时使用 `previous_response_id`：
  - history generation 未变化。
  - 当前逻辑 items 是上次已发送 items 的严格扩展。
  - model/instructions/tools/tool_choice/reasoning/include 等影响上下文的配置未变化。
  - 上次响应成功完成且 provider 声明可续接。
- 满足条件时只发送新增 items。
- compact、rollback、切模型、工具 schema 变化时清空 cursor 并全量重建。

### 12.4 Anthropic

贴近 Claude Code 的关键阶段：

- 历史消息不可变。
- image 直接进入用户消息或 `tool_result`。
- adapter 在最新合适的 content block 上添加 `cache_control`，逻辑 history 不保存该字段。
- cache TTL/策略在同一会话中应稳定，避免中途切换导致大前缀缓存抖动。

### 12.5 Cache 可观测性

现有 usage 归一化已支持 cached token 字段，可扩展记录：

```text
history_generation
request_message_count
request_logical_digest
stable_prefix_items
stable_prefix_bytes
image_count
image_visual_tokens_estimated
cache_read_tokens
cache_write_tokens
cache_hit_ratio
previous_response_id_used
cache_reset_reason
```

绝不能记录 raw request body。

## 14. 分阶段实施计划

### 阶段 0：冻结现状和建立回归基线

目标：在改变数据模型前，用测试固定当前协议和已知缺陷。

任务：

1. 增加 provider request capture 测试，记录一个含用户图片和两轮工具调用的完整消息序列。
2. 增加测试证明当前下一用户回合在旧图片位置发生前缀变化，作为待修复用例。
3. 增加 `load_image` 后重启/下一用户回合丢图的待修复用例。
4. 增加日志扫描测试，证明当前 logger 会收到 raw data URI；修复前可标为 expected failure。
5. 增加 mid-turn compact + 初始用户附件的待修复用例。

退出标准：关键问题都有可重复测试，不依赖真实 provider。

### 阶段 1：引入 MediaBlobStore 和 `ImageRef`

目标：先解决图片内容身份、稳定性和安全落盘，不改 provider 行为。

任务：

1. 实现 `ImageRef`、schema version、canonical JSON 和 SHA-256 校验。
2. 实现本地图片 ingest、大小/MIME/尺寸校验、内容寻址存储和原子写。
3. 把用户附件图片首次接收时复制到 blob store。
4. 提供 `ImageRef -> data URI` 确定性编码器。
5. 增加源文件覆盖、删除、重命名后仍能重放同一图片的测试。
6. 增加同一图片去重、损坏 blob 检测和并发写测试。

退出标准：同一个 `ImageRef` 跨进程还原的 data URI 完全相同。

### 阶段 2：逻辑消息与 provider 序列化分离

目标：history 保存 `ImageRef`，provider 请求才出现 base64。

任务：

1. 给 `Message` 增加 `image_ref` content part。
2. 新建 Chat Completions serializer，替代 `Message.to_dict()` 直接承担 provider 格式的方式。
3. `_build_chat_messages()` 接收逻辑 current user message，不接收“request_content/history_text”双份内容。
4. 用户回合成功后原样提交同一逻辑 user message。
5. transcript/active turn/compact payload 支持 image ref 往返。
6. 下一用户回合重新展开旧图片，并对比上一请求前缀字节。

退出标准：用户图片之后的上一轮 assistant/tool/final 仍能进入缓存稳定前缀；磁盘无 base64。

### 阶段 3：重构 `load_image`

目标：让工具图片成为正式、可恢复、带 call id 的工具内容。

任务：

1. 扩展 `ToolCallResult` 支持 `ToolModelResult` 和 `ImageRefPart`。
2. executor 把 call id 传入并保留在结构化结果中。
3. `load_image` 使用 MediaIngestor/BlobStore，不再自行 base64 + queue。
4. Chat adapter 稳定生成 tool 文本消息和 `tool_media_bridge` user 消息。
5. `ActiveTurn` 立即保存这两条逻辑内容，成功后一起 commit。
6. 支持批量并行工具调用时按原 tool call 顺序稳定展开图片，不能依赖线程完成顺序。
7. 删除空 call id 和临时缓冲依赖。
8. 保留非视觉 OCR 路径，并统一结果结构。

退出标准：`load_image` 图片跨工具轮、跨用户回合、跨重启都可重放，tool call 配对完整。

### 阶段 4：重写 compact 图片语义

目标：摘要输入无 base64，retained tail 和 active turn 不丢图。

任务：

1. 按完整用户回合和 tool protocol 切分 summarized prefix/retained tail。
2. 实现 `build_compaction_view()`，覆盖普通图片和 tool result 图片。
3. 摘要只覆盖 prefix，post-compact 按 `boundary + summary + tail` 安装。
4. retained tail 原样保留 image refs。
5. mid-turn compact 只处理 durable history，active turn 原样回挂。
6. active turn 自身超 hard limit 时停止并报错。
7. compact snapshot 保存 generation、覆盖范围、retained image count。
8. 视觉 token 估算接入 retained budget 和请求预算。

退出标准：compact 请求不含 raw base64；保留尾部图片仍可见；被摘要旧图只由摘要/标记代表；活动工具链不被拆散。

### 阶段 5：日志、恢复和 legacy migration

目标：堵住 base64 落盘并平滑升级现有会话。

任务：

1. MessageLogger 强制 redaction，所有 provider 图片形态均有测试。
2. active/pending/transcript/compact 加 schema version 和迁移器。
3. 对旧 history 中意外存在的 data URI：加载时解码、校验、写 blob、替换为 `ImageRef`。
4. 对当前版本只剩文本摘要的旧图片：不伪造恢复。若摘要中路径存在且 hash 匹配，可提供显式迁移工具；否则保留 legacy 文本语义。
5. 现有历史日志中的 base64 不应在启动时自动重写；提供独立审计/清理命令并先备份，避免破坏审计文件。
6. 实现 blob mark-and-sweep 和保留策略。

退出标准：新产生的 `.json/.jsonl/.log` 不含 `data:image` 或图片 base64；旧会话可读取。

### 阶段 6：Responses adapter

目标：在支持的 OpenAI provider 上贴近 Codex，减少全量图片重复传输。

任务：

1. 实现中立逻辑 item 到 Responses item 的映射。
2. 用户图片映射为 `input_image`。
3. `load_image` 映射为原生 function call output image。
4. thread id 映射为 `prompt_cache_key`。
5. 实现 `previous_response_id` cursor 和严格扩展校验。
6. compact/rollback/model/tool config 变化时重置 cursor。
7. provider 不支持时无缝回退 Chat adapter。

退出标准：连续工具轮和下一用户回合在可续接条件下仅发送增量 items。

### 阶段 7：Anthropic adapter

目标：贴近 Claude Code 的原生 image/tool_result/cache_control 行为。

任务：

1. 映射用户图片和 tool result 图片块。
2. 保持 tool_use/tool_result pairing。
3. 在 adapter 层应用稳定的 cache_control 策略。
4. 验证 compact view 去图片与 retained tail 保图。
5. 对 provider media item 上限实现“触发 compact/拒绝”策略，不允许静默改写已发送历史。

退出标准：Anthropic 请求协议原生、缓存标记稳定、history 仍为 provider-neutral。

## 15. 测试矩阵

### 15.1 用户附件

| 场景 | 预期 |
| --- | --- |
| 单图，无工具 | 当前请求可见图片；下一用户回合旧图片仍可重放 |
| 单图，多轮工具调用 | 所有工具轮前缀包含同一图片字节 |
| 下一轮再发新图 | 旧完整回合是新请求的稳定前缀，只追加新 user 图片 |
| 源文件被覆盖/删除 | 旧 ImageRef 仍还原原始字节 |
| 同图重复发送 | blob 去重，但逻辑消息各自存在 |
| 多图顺序 | 重启和不同工具调度下顺序不变 |
| 纯文本模型 | OCR 文本进入正式 history，不生成图片块 |

### 15.2 `load_image`

| 场景 | 预期 |
| --- | --- |
| 本地图片 | tool call id 与图片结果关联 |
| URL 图片 | 首次安全下载并固定内容，不依赖后续 URL 变化 |
| 同批多个 load_image | 按 tool call 原顺序展开，不按执行完成顺序 |
| load_image 后继续两个工具轮 | 图片消息不被替换或丢弃 |
| load_image 后用户发下一条消息 | 上一工具图片仍在正式历史中 |
| load_image 后进程崩溃 | active turn 恢复后仍能重放图片和 call id |
| 非视觉模型 | OCR tool result，无 bridge 图片消息 |

### 15.3 Compact

| 场景 | 预期 |
| --- | --- |
| 被摘要 prefix 含用户图 | 摘要请求只有图片标记，不含 base64 |
| 被摘要 prefix 含 tool 图片 | tool result 内图片变标记，call id 保留 |
| retained tail 含用户图 | compact 后仍保留 ImageRef 并可见 |
| retained tail 含 load_image | 完整 tool call/result/bridge 保留 |
| mid-turn 初始 user 含图 | compact durable history 后当前图片仍在 active turn |
| mid-turn 刚执行 load_image | 图片、tool result、call id 原样回挂 |
| active turn 自身超限 | 明确停止，不摘要活动工具链继续执行 |
| compact 失败 | history、generation、cursor、blob 引用全部不变 |

### 15.4 Cache 和序列化

核心测试不是“结构相等”，而是字节前缀相等：

```text
request_N_bytes == prefix(request_N_plus_1_bytes)
```

至少覆盖：

1. 用户图片之后有 assistant/tool/final。
2. `load_image` bridge 之后有 assistant/tool/final。
3. 会话保存、进程重启后再次构造。
4. 同一个 blob 在不同 Python 进程中 base64 编码。
5. tools schema 稳定排序和 provider adapter 默认字段稳定。
6. compact 后 generation 变化，预期不命中旧前缀；随后新 generation 再次稳定追加。

### 15.5 安全和落盘

递归扫描测试目录中的：

```text
.cbagent/sessions/**/*.json*
.cbagent/logs/**/*
.cbagent/tool_results/**/*
```

断言：

- 不出现 `data:image/`。
- 不出现已知测试 base64 secret。
- blob 文件字节存在且 hash 正确。

## 16. 验收标准

重构完成必须同时满足以下条件：

1. 普通用户回合结束后，不再把模型已见的图片消息替换成文本版历史。
2. 下一用户回合中，上一轮从图片消息开始到最终回答的 provider payload 与首次发送完全一致。
3. history/transcript/compact/active checkpoint 不保存 raw base64，只保存 `ImageRef`。
4. `load_image` 不再依赖 `pending_images`，图片结果带真实 call id 并进入正式历史。
5. Chat、Responses、Anthropic 的图片协议差异只存在于 adapter，不污染核心 history。
6. compact 摘要请求不发送图片 base64。
7. compact retained tail 中的用户图片和 tool 图片仍能被下一次正常模型请求看到。
8. mid-turn compact 不摘要或拆散当前 active turn；活动回合过大时安全停止。
9. token 预算包含视觉 token，不把 image ref 当成零成本。
10. MessageLogger、transcript 和诊断输出都不会泄漏 raw base64。
11. compact/rollback/clear 是唯一正常 history rewrite 边界，并有 generation/cursor reset 记录。
12. 测试能量化 Prompt Cache 命中改善，而不只验证“模型还能回答”。

## 17. 风险、取舍和明确不做的事

### 17.1 磁盘占用会增加

保存 blob 比只保存文本摘要占空间，但这是可重放多模态上下文的必要成本。内容寻址去重、尺寸上限、规范化和 GC 可控制增长。不能通过修改已发送历史来节省磁盘。

### 17.2 Chat Completions 仍会重复传输 base64

稳定 Prompt Cache 解决模型重复 prefill，不保证请求体不重复上传。若图片较大，Responses `previous_response_id`、provider file ID 或稳定对象存储才是传输优化方案。

### 17.3 Compact 不应尝试“重新理解”旧图片

摘要模型默认不接收旧原图。它从图片标记和后续 assistant 分析中生成 handoff。若业务要求视觉摘要，应设计显式的“图片描述 artifact”流程，在图片首次进入上下文时生成并作为独立文本事实保存，而不是在 compact 时临时重读所有图片。

### 17.4 不自动恢复已经丢失的旧图片语义

当前版本历史只保留文本摘要时，原图可能已不存在或已被覆盖。迁移器不能仅根据 filepath 盲目重新读取并声称它是模型当时见过的图片；必须校验原 hash。无法校验时保留 legacy 文本即可。

### 17.5 不依赖 JSON key 顺序作为唯一协议保证

缓存测试应使用真实 SDK 最终请求或稳定 canonical serializer。逻辑 digest 用于检测内部改写，不能替代对 provider payload 的集成测试。

## 18. 推荐实施顺序和优先级

建议按以下优先级推进：

```text
P0  MediaBlobStore + ImageRef
P0  用户附件改为统一逻辑消息并跨轮重放
P0  MessageLogger/base64 落盘修复
P0  load_image 结构化结果 + 正式 history
P0  compact view 去图片 + retained tail 保图 + active turn 隔离
P1  视觉 token 统一估算和缓存可观测性
P1  legacy migration + blob GC
P1  Responses adapter + previous_response_id + prompt_cache_key
P2  Anthropic adapter + cache_control
```

不建议先单独修改 `history_text` 为 filepath。filepath 不是不可变内容，也不能表达工具图片归属、跨进程一致性、URL 固定、compact retained 语义和 provider adapter 差异。正确的最小核心是 `ImageRef + BlobStore + 逻辑消息冻结`。

## 19. 最终目标时序

### 用户附件

```text
用户发送 image.png
  -> ingest once
  -> blob sha256:X
  -> U1[text, ImageRef(X)] 写 ActiveTurn
  -> Chat adapter 临时生成 BASE64_X
  -> tool loop 全程 append
  -> U1 原样 commit 到 history
  -> 下一用户回合再次由 X 生成相同 BASE64_X
  -> 旧完整回合继续作为缓存前缀
```

### `load_image`

```text
assistant 调用 load_image(call_123)
  -> ingest once -> ImageRef(Y)
  -> ToolResult(call_123, text, ImageRef(Y)) 写 ActiveTurn
  -> Chat adapter: role=tool + stable role=user bridge
     或 Responses: function_call_output(input_image)
     或 Anthropic: tool_result(image)
  -> 后续工具轮继续 append
  -> 成功后正式 commit
  -> 重启/下一用户回合仍可重放
```

### Compact

```text
durable history = old_prefix + recent_tail
active turn     = current_user_image + tool chain + load_image result

compact:
  old_prefix -> compaction_view（图片变标记）-> summary
  recent_tail -> 原样保留 ImageRef
  active turn -> 完全不参与摘要，原样保留

new generation = boundary + summary + recent_tail + active turn
```

这样，CbAgent 才真正具备与 Codex/Claude Code 相近的多模态上下文语义：磁盘安全、逻辑历史真实、工具协议完整、compact 可控、普通回合缓存前缀稳定，并为 Responses 增量续接留出清晰的 provider 边界。
